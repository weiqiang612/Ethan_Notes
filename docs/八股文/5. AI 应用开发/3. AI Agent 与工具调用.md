## 🎯 简历亮点深度关联与大厂面试预测

### 1. Agent Loop 与【sky-ai Advisor 链调度管道】
*   **面试官切入点**：
    > "你实现的 AI 客服 Agent 是一个典型的 Agent Loop 吗？请讲一下你的 Agent 一次完整请求的循环流程，以及你是如何控制循环终止的。"
*   **袁志刚专属特训回答模版**：
    1.  **Agent Loop 的标准定义**：Agent Loop 是指 Agent 在接收到用户输入后，进入一个 **"观察 → 规划 → 行动 → 反思"** 的循环。每一轮循环中，Agent 观察当前状态和上下文，规划下一步操作，执行工具调用或生成回复，然后反思执行结果决定是否需要继续循环。
    2.  **sky-ai 的 Agent Loop 实现**：我们的 Agent 管道是一个基于 **Spring AI Advisor 责任链** 的 Agent Loop：
        *   **观察阶段**：`IntentRecognitionAdvisor`（Order=HIGHEST_PRECEDENCE）通过调用 `CustomerIntentRecognitionService.recognize()` 分析用户输入，结合 `ChatHistoryService` 构建的对话历史和用户画像摘要，识别出意图类型和实体信息，放入 `ChatClientRequest.context()` 中。
        *   **规划阶段**：`UserContextAdvisor`（Order=HIGHEST_PRECEDENCE+1）根据意图类型，通过 `allowedTools()` 方法生成动态工具白名单（二级授权：domain 基础工具 + intent 专属工具），同时按 `ProfileInjectionLevel`（NONE/SUMMARY/FULL）注入用户记忆上下文。
        *   **知识增强**：`RagAdvisor`（Order=HIGHEST_PRECEDENCE+3）通过 `OnlineRetrievalService` 从向量库检索 FAQ 知识，以 SystemMessage 形式注入 Prompt。
        *   **行动阶段**：`ToolFilterAdvisor`（Order=HIGHEST_PRECEDENCE+4）从 `DynamicToolCallbackRegistry` 中按白名单筛选 `ToolCallback` 列表并注入 Prompt Options。模型根据工具声明决定是否调用工具。
        *   **反思与熔断**：`SafeToolCallAdvisor`（Order=LOWEST_PRECEDENCE-100）继承 `ToolCallAdvisor`，在每轮工具调用后进行签名检测（`signature(toolCall)` = 工具名 + 参数哈希）。如果发现重复签名或超过 `MAX_TOOL_CALL_ROUNDS = 4` 轮，立即 `stop()` 熔断，返回友好提示"已查询到的信息不足以继续自动处理，请你确认一下需要的菜品或改用更明确的说法"。

#### 🖥️ 核心支撑源码：Agent 意图识别与入口编排
```java
// AgentChatService.java - 责任链及入口管道编排
public String ask(String question, String conversationId, String userId, IntentRecognitionResult preIntent) {
    // 1. 调用 executeCall 触发 ChatClient.Builder 并挂载责任链
    ChatClientResponse response = executeCall(question, conversationId, userId, preIntent, Map.of());
    return extractAnswer(response);
}

private ChatClientResponse executeCall(String question, String conversationId, String userId, 
                                       IntentRecognitionResult preIntent, Map<String, Object> extraContext) {
    Map<String, Object> contextParams = new java.util.LinkedHashMap<>();
    contextParams.put(ChatMemory.CONVERSATION_ID, conversationId);
    contextParams.put("userId", userId);
    
    return chatClientBuilder.build().prompt()
            .advisors(advisors(preIntent).toArray(CallAdvisor[]::new)) // 装载拦截器责任链
            .advisors(advisor -> contextParams.forEach(advisor::param))
            .toolContext(Map.of("userId", userId)) // 将用户ID作为上下文传给 Function 工具做越权防御
            .user(question)
            .call()
            .chatClientResponse();
}
```

### 2. Agent Memory 与【sky-ai 用户记忆系统】
*   **面试官切入点**：
    > "你的 Agent 有一个完整的用户记忆系统，包括偏好菜品、口味偏好、饮食禁忌等。请问你的短期记忆和长期记忆是如何设计的？不同的意图场景下记忆注入粒度是如何控制的？"
*   **袁志刚专属特训回答模版**：
    1.  **短期记忆（Session Memory）**：
        *   由 `ChatHistoryService` 管理。基于 Spring AI 的 `ChatMemory` 接口，以 `conversationId` 为键存储当轮对话的消息列表。
        *   作用：维持当轮对话上下文连贯性，让 Agent 记住用户在本次对话中说过什么。
        *   生命周期：跟随会话生命周期，会话结束后可选择性持久化或清除。
    2.  **长期记忆（Persistent Memory）**：
        *   由 `UserMemoryFactService` 管理。使用 `UserMemoryFact` 实体持久化到数据库。
        *   6 种记忆维度（`MemoryFactKey`）：`FAVORITE_DISHES`、`FAVORITE_FLAVORS`、`DIETARY_RESTRICTIONS`、`DEFAULT_ADDRESS`、`OPERATIONAL_NOTES`、`USER_PROFILE_NOTES`。
        *   记忆来源区分（`MemoryFactSourceType`）：`USER_MANUAL`（用户显式设定）和系统自动提取，显示时标注 `[用户自设]`。
        *   `MemoryWriterService` 负责从对话中自动提取和更新用户偏好记忆。
    3.  **意图驱动的分级记忆注入**：
        ```
        SHOP_STATUS           → ProfileInjectionLevel.NONE    → 不注入任何记忆
        ORDER_STATUS/CANCEL   → ProfileInjectionLevel.SUMMARY → 注入画像摘要
        MENU_QUERY/CART       → ProfileInjectionLevel.FULL    → 注入完整画像 + 偏好菜品/口味/禁忌
        ```
    4.  **记忆参与意图识别**：`IntentRecognitionAdvisor` 在调用意图识别 LLM 前，会将用户画像摘要拼接到用户消息前（`"User profile notes: " + summary + "\n" + userText`），提升意图识别精度。

```java
// UserContextAdvisor.java - 根据意图动态过滤工具并注入记忆上下文
@Override
public ChatClientResponse adviseCall(ChatClientRequest chatClientRequest, CallAdvisorChain callAdvisorChain) {
    IntentRecognitionResult intentResult = resolveIntent(chatClientRequest);
    
    // 1. 防御性拷贝只读上下文，注入允许的工具白名单
    Map<String, Object> context = new java.util.HashMap<>(chatClientRequest.context());
    context.put("allowedTools", allowedTools(intentResult));
    
    String userId = stringParam(chatClientRequest, "userId");
    String contextBlock = buildContextBlock(chatClientRequest, intentResult, userId);
    
    // 2. 使用 Builder 模式重新生成不可变的 ChatClientRequest，防止状态修改丢失
    ChatClientRequest.Builder builder = chatClientRequest.mutate().context(context);
    if (StringUtils.hasText(contextBlock)) {
        List<Message> instructions = new ArrayList<>(chatClientRequest.prompt().getInstructions());
        instructions.add(0, new SystemMessage(contextBlock)); // 将用户记忆上下文强插首位以防长上下文失忆
        builder.prompt(new Prompt(instructions, chatClientRequest.prompt().getOptions()));
    }
    return callAdvisorChain.nextCall(builder.build());
}

// 动态意图工具白名单授权（沙箱权限隔离）
private Set<String> allowedTools(IntentRecognitionResult intentResult) {
    if (intentResult == null || !intentResult.intent().isTask()) return Set.of();
    
    // 第一级：domain 基础工具集
    Set<String> base = switch (intentResult.intent().domain()) {
        case ORDER   -> setOf("searchOrders", "getOrderDetail", "listRecentOrders");
        case MENU    -> setOf("searchDishes", "searchSetmeals");
        case ADDRESS -> setOf("searchAddresses", "listAddresses");
        case SHOP    -> setOf("getShopStatus");
    };
    // 第二级：intent 专属操作工具
    Set<String> extra = switch (intentResult.intent()) {
        case CANCEL_ORDER   -> setOf("cancelOrder");
        case REQUEST_REFUND -> setOf("requestRefund");
        case CHANGE_ADDRESS -> setOf("updateDeliveryAddress");
        default             -> Set.of();
    };
    Set<String> merged = new LinkedHashSet<>(base);
    merged.addAll(extra);
    return merged;
}
```
> [!NOTE]
> **🔥 大厂生产级踩坑/高并发避坑提示（面试高分吹水点）**：
> 早期版本在 `UserContextAdvisor` 拦截器里直接通过 `chatClientRequest.context().put(...)` 进行侧面突变。在生产环境高并发下，框架返回的 `context` 有时是不可变的（例如 `Collections.unmodifiableMap` 包装），直接调用会抛出 `UnsupportedOperationException`；同时由于没有调用 `.mutate()` 重构，导致在非分支突变时上下文可能丢失。后经过我们**重构为 Builder 不可变拷贝模式**，优雅解决了该线上隐患。

### 3. 工具调用安全与【SafeToolCallAdvisor 熔断机制】
*   **面试官切入点**：
    > "在生产环境中，Agent 的工具调用可能出现死循环——比如模型反复调用同一个工具且参数一致。你是如何防止这种情况的？"
*   **袁志刚专属特训回答模版**：
    1.  **签名检测机制**：`SafeToolCallAdvisor` 在 `guard()` 方法中，为每次工具调用生成 **签名哈希**（`toolCall.name() + "\0" + toolCall.arguments().trim()`）。通过 `LoopState` 内部类维护当前会话的 `seenToolCalls`（已见签名集合）和 `toolCallRounds`（调用轮次计数）。
    2.  **双重熔断条件**：
        *   **签名重复**：如果同一轮次内出现重复签名，或者跨轮次出现历史已见的签名，立即触发熔断。
        *   **轮次超限**：工具调用轮次超过 `MAX_TOOL_CALL_ROUNDS = 4`，触发熔断。
    3.  **优雅降级**：熔断后通过 `chatClientResponse.mutate().chatResponse(fallback).build()` 替换模型原始回复为友好的用户提示，而不是抛异常导致系统崩溃。

#### 🖥️ 核心支撑源码：工具调用签名防重与死循环熔断
```java
// SafeToolCallAdvisor.java - 死循环防重熔断拦截器
private ChatClientResponse guard(ChatClientResponse chatClientResponse) {
    if (chatClientResponse == null || chatClientResponse.chatResponse() == null
            || chatClientResponse.chatResponse().getResult() == null) {
        return chatClientResponse;
    }
    AssistantMessage assistantMessage = chatClientResponse.chatResponse().getResult().getOutput();
    if (assistantMessage == null || !assistantMessage.hasToolCalls()) {
        return chatClientResponse;
    }
    
    LoopState loopState = state(chatClientResponse.context());
    Set<String> signatures = new HashSet<>();
    for (AssistantMessage.ToolCall toolCall : assistantMessage.getToolCalls()) {
        String signature = toolCall.name() + "\u0000" + (toolCall.arguments() == null ? "" : toolCall.arguments().trim());
        // 核心拦截：检测当前轮次是否重复，或者是否调用了历史已见过的相同参数工具
        if (!signatures.add(signature) || loopState.seenToolCalls.contains(signature)) {
            return stop(chatClientResponse); // 熔断拦截，短路大模型并输出兜底话术
        }
    }
    if (loopState.toolCallRounds >= MAX_TOOL_CALL_ROUNDS) { // 轮次超限强熔断（防止无限 Loop 耗尽 Token）
        return stop(chatClientResponse);
    }
    loopState.toolCallRounds++;
    loopState.seenToolCalls.addAll(signatures);
    return chatClientResponse;
}

private ChatClientResponse stop(ChatClientResponse chatClientResponse) {
    ChatResponse fallback = ChatResponse.builder()
            .from(chatClientResponse.chatResponse())
            .generations(List.of(new Generation(AssistantMessage.builder().content(STOP_MESSAGE).build())))
            .build();
    return chatClientResponse.mutate().chatResponse(fallback).build();
}
```

## 🚀 第一优先级核心考点详解（Agent 核心概念、Agent vs Workflow、Context Engineering）

### 一、 AI Agent 核心概念

#### 1. Agent 的定义
AI Agent 是一个能够**自主感知环境、做出决策、采取行动**的智能系统。与传统的 Chatbot 不同，Agent 具备：
*   **自主决策**：不依赖预定义的固定流程，而是根据当前状态和目标自主规划行动路径。
*   **工具使用**：能够调用外部工具（API、数据库、搜索引擎等）来获取信息或执行操作。
*   **持续交互**：在一个 Loop 中持续运行，直到任务完成或达到终止条件。

#### 2. Agent 与 Workflow/Chatbot 的本质区别
| 维度 | Chatbot | Workflow | Agent |
| :--- | :--- | :--- | :--- |
| **决策方式** | 规则匹配 / 单轮生成 | DAG 预定义流程 | LLM 自主规划 |
| **流程控制** | 无流程 | 开发者设计固定路径 | Agent 自主选择路径 |
| **工具使用** | 无 | 固定节点调用固定工具 | 动态选择工具和参数 |
| **循环能力** | 无 | 条件分支 | 自主 Loop（观察→规划→行动→反思） |
| **适用场景** | 简单问答 | 确定性强的业务流程 | 不确定性高、需要灵活应对的任务 |

#### 3. Agent Loop 的核心循环
```
┌─────────────────────────────────────────────┐
│                 Agent Loop                  │
│                                             │
│  1. 观察 (Observe)                          │
│     - 接收用户输入                            │
│     - 读取环境状态和上下文                      │
│                                             │
│  2. 规划 (Plan)                             │
│     - LLM 分析意图                            │
│     - 决定调用哪些工具/生成回复                  │
│                                             │
│  3. 行动 (Act)                              │
│     - 执行工具调用                             │
│     - 获取工具执行结果                          │
│                                             │
│  4. 反思 (Reflect)                          │
│     - 评估行动结果                             │
│     - 决定是否继续循环                          │
│     - 如果任务完成 → 退出 Loop                 │
│     - 如果需要更多信息 → 回到步骤 1              │
│                                             │
│  终止条件：                                   │
│     - 任务完成                                │
│     - 达到最大轮次                             │
│     - 触发熔断（签名重复/死循环检测）              │
│     - Token 预算耗尽                          │
└─────────────────────────────────────────────┘
```

### 二、 Prompt Engineering vs Context Engineering

#### 1. Prompt Engineering（提示词工程）
*   **定义**：设计和优化给 LLM 的指令文本，引导模型按期望方式输出。
*   **四要素**：角色设定（Role）、指令（Instruction）、输入数据（Input）、输出格式（Output Format）。
*   **常见技巧**：
    *   **Few-Shot**：在 Prompt 中给出几个示例，帮助模型理解期望格式。
    *   **Chain-of-Thought (CoT)**：要求模型"一步步思考"，提升推理质量。
    *   **ReAct**：结合推理和行动（Reasoning + Acting），让模型先分析再决策。
*   **Prompt 注入防护**：用户可能通过精心构造的输入覆盖 System Prompt。防御方式包括输入过滤、Prompt 分层隔离、输出安全校验。

#### 2. Context Engineering（上下文工程）
*   **定义**：不仅仅是写好 Prompt，而是**系统性地管理 LLM 在每次调用时能看到的所有信息**——包括 System Instructions、用户画像、对话历史、检索结果、工具定义和中间结果。
*   **与 Prompt Engineering 的区别**：Prompt Engineering 关注"怎么写指令"；Context Engineering 关注"把什么信息、以什么顺序、在什么时机放进上下文窗口"。
*   **在 sky-ai 中的体现**：
    *   **静态规则编排**：System Prompt 定义 Agent 的角色和行为规范。
    *   **动态信息挂载**：`UserContextAdvisor` 根据意图类型动态注入不同粒度的用户记忆；`RagAdvisor` 根据用户提问检索知识库并注入上下文。
    *   **Token 预算降级**：不同意图对应不同的 `ProfileInjectionLevel`，避免简单查询浪费 Token。
    *   **上下文排序策略**：用户画像和 RAG 上下文都通过 `instructions.add(0, new SystemMessage(...))` 放在首位，利用模型对开头信息的高关注度。

## 🛠️ 第二优先级核心考点详解（MCP 协议、Agent Skills、Harness Engineering、AI 工作流）

### 一、 MCP 协议（Model Context Protocol）

#### 1. MCP 解决什么问题
在 AI 应用中，每个工具提供商（如邮件服务、数据库、搜索引擎）的 API 格式各不相同。Function Calling 虽然解决了模型与工具的交互协议，但每个工具的注册、鉴权、调用方式仍然高度碎片化。MCP 通过标准化协议解决这个问题。

#### 2. MCP 的分层架构
| 层次 | 组件 | 职责 |
| :--- | :--- | :--- |
| **MCP Client** | 嵌入在 AI 应用中 | 发现和连接 MCP Server，转发工具调用 |
| **MCP Server** | 独立部署的工具服务 | 暴露工具定义、执行工具调用、管理鉴权 |
| **MCP Protocol** | 传输协议（JSON-RPC 2.0） | 标准化请求/响应格式 |

#### 3. MCP vs Function Calling vs Tool Calling 对比
| 维度 | Function Calling | Tool Calling | MCP |
| :--- | :--- | :--- | :--- |
| **抽象级别** | 单函数声明 | 多函数并行 | 标准化协议 + 工具服务生态 |
| **工具管理** | 硬编码在客户端 | 硬编码在客户端 | 独立部署的 MCP Server |
| **鉴权** | 客户端自行处理 | 客户端自行处理 | MCP Server 统一管理 |
| **可发现性** | 无 | 无 | 支持动态工具发现 |
| **适用场景** | 简单工具调用 | 多工具并行 | 企业级工具生态 |

#### 4. 生产级 MCP 的安全治理
*   **权限隔离**：不同用户/角色对同一工具的访问权限不同。
*   **操作审计**：记录每次工具调用的调用方、参数、结果和时间。
*   **输入校验**：防止 LLM 生成恶意参数（如 SQL 注入、命令注入）。
*   **速率限制**：对高风险工具（如删除、支付）实施调用频次限制。

### 二、 Agent Skills（技能）

#### 1. Skills 与 Prompt/MCP/Function Calling 的区别
*   **Prompt**：文本指令，告诉模型"怎么做"。
*   **Function Calling**：声明可用函数，让模型"能做什么"。
*   **MCP**：标准化的工具注册与调用协议。
*   **Skills**：**可复用的知识与工作流包**——将 Prompt 模板、工具定义、执行逻辑和领域知识打包成一个可插拔的技能单元。

#### 2. Skills 的核心价值
*   **可复用性**：同一个 Skill 可以被不同 Agent 加载和使用。
*   **可组合性**：多个 Skills 可以组合形成复杂的 Agent 能力。
*   **版本管理**：每个 Skill 可以独立迭代和版本控制。

### 三、 Harness Engineering

#### 1. 什么是 Harness
Harness 是围绕 LLM 的**整个工程支撑骨架**——包括 Prompt 管理、上下文编排、工具注册、Memory 管理、安全过滤、输出校验和监控告警。

#### 2. Model + Harness 架构
*   **Model**：大模型本身，负责推理和生成。
*   **Harness**：所有非模型部分的工程化基础设施。
*   **核心观点**：一个 AI 应用的质量，30% 取决于模型能力，70% 取决于 Harness 工程。

### 四、 AI 工作流（Workflow、Graph、Loop）

#### 1. 三种编排模式
*   **Workflow（工作流）**：线性或分支的 DAG 流程，节点和边在开发时就确定。适合确定性高的场景。
*   **Graph（图）**：节点之间有复杂的跳转和条件路由，支持环和回溯。适合需要动态路由的复杂流程。
*   **Loop（循环）**：Agent 的核心编排模式——持续循环直到目标达成或终止条件触发。适合不确定性高、需要多步推理的任务。

#### 2. 在 sky-ai 中的体现
我们的 Agent 采用的是 **Advisor Chain + Loop** 的混合模式：
*   **Advisor Chain**：线性责任链（Workflow 模式），每个 Advisor 按 Order 顺序依次执行。
*   **Tool Call Loop**：`SafeToolCallAdvisor` 继承的 `ToolCallAdvisor` 内置了工具调用循环——模型决定调用工具 → 执行工具 → 结果回传模型 → 模型决定是否继续调用。
*   **Loop 终止**：签名重复检测 + 轮次上限（4 轮）+ 模型自行决定停止调用工具。
