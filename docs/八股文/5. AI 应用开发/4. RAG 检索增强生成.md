*   **面试官切入点**：
    > "你的 AI 客服项目中集成了 RAG 检索增强，请完整描述一下你的 RAG 链路——从文档入库到检索到生成的全过程。"
*   **袁志刚专属特训回答模版**：
    1.  **离线索引管道 (`rag/offline/`)**：
        *   **文档解析 (`parse/`)**：将原始文档（FAQ 文本、Markdown、PDF 等）解析为结构化纯文本。
        *   **文档分块 (`chunk/`)**：将长文档按语义或固定长度切分为小块（Chunk），每个 Chunk 作为一个独立的检索单元。
        *   **向量化 (`index/`)**：使用 Embedding 模型将每个 Chunk 转化为高维向量表示。
        *   **向量存储 (`store/`)**：将向量和元数据存入 **PgvectorVectorStore**（PostgreSQL + pgvector 扩展）。Spring AI 通过自动装配将 `PgvectorVectorStore` Bean 注入 IoC 容器，底层配置通过 `@ConditionalOnClass(PgvectorVectorStore.class)` 条件注解触发。

        *   **查询接收**：`RagAdvisor`（Order=HIGHEST_PRECEDENCE+3）从 `ChatClientRequest` 中提取用户消息文本。
        *   **向量检索**：`OnlineRetrievalService.retrieve(userText)` 将用户消息向量化，在 PgvectorVectorStore 中进行相似性搜索，返回 `RetrievalResult`。
        *   **上下文注入**：将检索到的知识以 `"使用以下检索上下文回答问题：\n" + retrievalResult.context()` 的格式，通过 `SystemMessage` 注入到 Prompt 首位。
    3.  **与 Advisor 链的集成顺序**：
        *   意图识别 → 用户画像注入 → **RAG 检索** → 工具过滤 → 工具调用
        *   RAG 在工具过滤之前执行，确保模型在决定是否使用工具之前已经拥有了知识库的背景信息。

### 2. PgvectorVectorStore 与【向量数据库工程选型】
*   **面试官切入点**：
    > "你为什么选择 Pgvector 而不是 Milvus、Pinecone 或 Qdrant？Pgvector 的优势和局限性是什么？"
*   **袁志刚专属特训回答模版**：
    1.  **选择 Pgvector 的理由**：
        *   **技术栈统一**：我们的苍穹外卖项目已经使用 PostgreSQL 作为主数据库。使用 pgvector 扩展可以在同一个数据库实例中同时存储业务数据和向量数据，避免引入额外的中间件运维成本。
        *   **Spring AI 原生支持**：Spring AI 提供了 `PgvectorVectorStore` 的自动装配 Starter，只需在 `pom.xml` 引入依赖并配置 YAML，即可通过 `@ConditionalOnClass` 自动注入 Bean。
        *   **事务一致性**：业务数据和向量数据在同一个 PostgreSQL 事务中，可以保证数据一致性。
    2.  **Pgvector 的局限性**：
        *   **大规模性能**：当向量数量超过千万级时，Pgvector 的检索性能不如专用向量数据库（如 Milvus）。
        *   **索引类型有限**：Pgvector 主要支持 IVFFlat 和 HNSW 索引，专用向量数据库提供更多优化选项。
        *   **不支持分布式**：Pgvector 是单机扩展，不具备 Milvus 的分布式横向扩展能力。
    3.  **适用场景结论**：对于中小规模知识库（10 万条以内）且已使用 PostgreSQL 的项目，Pgvector 是性价比最高的选择。

## 🚀 第一优先级核心考点详解（RAG 核心概念、文档处理、向量索引）

### 一、 RAG 核心概念

#### 1. RAG 是什么
RAG（Retrieval-Augmented Generation，检索增强生成）是一种将 **信息检索** 与 **语言模型生成** 相结合的技术架构。它通过在生成之前先从外部知识库检索相关信息，将检索结果作为上下文注入模型，从而让模型基于真实证据进行回答，而非完全依赖模型参数中的"记忆"。

#### 2. 为什么需要 RAG
*   **减少幻觉**：模型基于检索到的真实文档生成答案，而非凭空编造。
*   **知识时效性**：模型参数在训练后就固定了，但 RAG 的知识库可以随时更新。
*   **领域专业性**：将企业私有知识注入模型，无需微调。
*   **可追溯性**：答案可以关联到具体的源文档，方便审计。

#### 3. RAG 完整链路
```
                    离线索引管道
┌──────────────────────────────────────────────┐
│  原始文档 → 解析 → 清洗 → 分块 → Embedding → 向量存储  │
└──────────────────────────────────────────────┘

                    在线检索管道
┌──────────────────────────────────────────────────────┐
│  用户提问 → Query 处理 → 向量检索 → 重排序 → 上下文组装 → LLM 生成  │
└──────────────────────────────────────────────────────┘
```

### 二、 文档处理与 Chunk 切分策略

#### 1. 文档解析
*   **PDF**：需要处理布局、表格、图片等复杂元素。工具选择：PyMuPDF、Unstructured、Marker。
*   **Markdown/TXT**：相对简单，按标题和段落结构化。
*   **FAQ**：问答对格式，每个 Q&A 作为一个独立 Chunk 最佳。

#### 2. Chunk 切分策略对比
| 策略 | 切分方式 | 优点 | 缺点 | 适用场景 |
| :--- | :--- | :--- | :--- | :--- |
| **固定长度** | 按字符/Token 数固定切分 | 实现简单 | 可能切断语义 | 通用文本 |
| **句子级** | 按句号/换行分割 | 保持句子完整 | 粒度可能太细 | 对话记录 |
| **段落级** | 按段落分割 | 保持段落语义 | 段落长度不均 | 文章/报告 |
| **语义切分** | 按语义相似度聚类分割 | 语义完整性最佳 | 计算成本高 | 复杂文档 |
| **滑动窗口** | 固定长度 + 重叠 | 防止信息丢失 | 增加索引量 | 长文本 |
| **递归切分** | 多级分隔符层层尝试 | 平衡粒度和语义 | 配置复杂 | 通用场景（推荐默认） |

#### 3. Chunk 大小的影响
*   **Chunk 太大**：检索精度下降（相关信息被大量无关文本稀释），Token 消耗增加。
*   **Chunk 太小**：语义不完整，模型缺乏足够上下文理解。
*   **经验值**：通常 200-1000 Token 为宜。FAQ 场景推荐以完整 Q&A 为单位；长文档推荐 500 Token + 50 Token 重叠。

### 三、 向量索引算法与向量数据库

#### 1. Embedding 模型
将文本转化为高维向量的模型。核心指标包括：
*   **维度**：向量维度越高，表达能力越强，但计算成本也越高。常见维度：768、1024、1536。
*   **相似度计算**：余弦相似度（Cosine Similarity）最常用。

#### 2. 核心向量索引算法

##### HNSW (Hierarchical Navigable Small World)
*   **原理**：构建多层的小世界图。底层包含所有向量，高层是底层的稀疏采样。查询时从最高层开始贪婪搜索，逐层下降到底层精确搜索。
*   **核心参数**：
    *   `M`：每个节点的最大邻居数。越大越精确，构建时间和内存越高。
    *   `efConstruction`：构建时的动态候选列表大小。
    *   `efSearch`：查询时的动态候选列表大小。越大越精确，查询越慢。
*   **优势**：查询速度极快（对数复杂度），精度高。
*   **劣势**：内存占用大（需要将图结构全部加载到内存），构建时间长。
*   **适用场景**：数据量中等（百万级）、对查询延迟要求高的场景。

##### IVFFlat (Inverted File with Flat Quantization)
*   **原理**：先用 K-Means 将向量聚类为 N 个聚类中心（称为 nlist）。查询时先找到最近的 nprobe 个聚类中心，再在这些聚类内做精确搜索。
*   **核心参数**：
    *   `nlist`：聚类数量。越多越精确，但每个聚类内的向量越少。
    *   `nprobe`：查询时搜索的聚类数。越多越精确，查询越慢。
*   **优势**：内存占用低，支持增量写入。
*   **劣势**：精度不如 HNSW，需要预先训练聚类中心。
*   **适用场景**：数据量大（千万级以上）、内存受限的场景。

#### 3. 向量数据库选型
| 数据库 | 类型 | 分布式 | 适用规模 | 特点 |
| :--- | :--- | :--- | :--- | :--- |
| **Pgvector** | PostgreSQL 扩展 | 否 | 10万级 | 与业务库合一，事务一致 |
| **Milvus** | 专用向量数据库 | 是 | 亿级 | 高性能，丰富的索引类型 |
| **Qdrant** | 专用向量数据库 | 是 | 千万级 | Rust 编写，性能优异 |
| **Pinecone** | 云托管 | 是 | 任意 | 全托管，零运维 |
| **Elasticsearch** | 搜索引擎 + 向量 | 是 | 亿级 | 混合检索原生支持 |

## 🛠️ 第二优先级核心考点详解（检索优化、GraphRAG、知识库更新）

### 一、 RAG 检索优化

#### 1. 召回率低的排查路线
```
RAG 效果差 →
├── 正确文档是否在候选池？
│   ├── 否 → 排查：
│   │   ├── 文档解析是否完整（PDF 表格、图片是否丢失）
│   │   ├── Chunk 策略是否合理（是否切断了关键信息）
│   │   ├── Embedding 模型是否适合当前领域
│   │   ├── Metadata 过滤是否过于严格
│   │   └── Query 改写是否到位
│   └── 是 → 排查：
│       ├── 排序是否正确（Rerank 是否生效）
│       ├── Top-K 是否太小
│       ├── Hybrid Search 权重是否合理
│       └── 候选池大小是否足够
└── 正确文档在上下文中但答案仍错 →
    ├── Prompt 是否引导模型使用检索结果
    ├── 检索结果在上下文中的位置（首部 vs 中间）
    ├── 模型是否忠实使用证据（Faithfulness）
    └── 模型是否理解了问题意图
```

#### 2. Query Rewrite（查询改写）
*   **为什么需要**：用户的原始提问往往口语化、模糊、含有代词。直接用原始 query 检索效果很差。
*   **改写方式**：
    *   **LLM 改写**：用 LLM 将用户问题改写为更适合检索的形式。
    *   **HyDE (Hypothetical Document Embeddings)**：用 LLM 先生成一个"假想答案"，用假想答案而非原始问题去检索。
    *   **多查询扩展**：将一个问题扩展为多个角度的子查询，分别检索后合并结果。

#### 3. Hybrid Search（混合检索）
*   **纯向量检索的局限**：语义检索擅长理解含义，但对精确关键词匹配（如订单号、菜品名称）不敏感。
*   **混合检索方案**：
    *   **向量检索**（语义匹配）+ **关键词检索**（BM25 精确匹配）
    *   **融合策略**：RRF (Reciprocal Rank Fusion) 将两路结果按排名倒数加权合并。

#### 4. Rerank（重排序）
*   **为什么需要**：初始检索（ANN 近似最近邻）为了速度会牺牲一些精度。Rerank 用更精确但更慢的模型对初始检索结果重新排序。
*   **方式**：使用 Cross-Encoder 对 (query, document) 对进行精细打分。
*   **典型流程**：初始检索 Top-50 → Rerank → 取 Top-5 送入 LLM。

### 二、 GraphRAG

#### 1. GraphRAG 是什么
传统 RAG 将文档切成独立的 Chunk，丢失了文档间的关联关系。GraphRAG 通过构建**知识图谱**（实体 + 关系），将文档中的知识结构化为图，支持基于图关系的检索和推理。

#### 2. GraphRAG 的核心流程
1.  **实体和关系提取**：用 LLM 从文档中抽取实体（人物、组织、概念等）和它们之间的关系。
2.  **社区发现**：用 Leiden 等算法将图中紧密关联的实体聚类为"社区"。
3.  **社区摘要生成**：为每个社区生成文本摘要，作为高层知识的检索单元。
4.  **检索方式**：
    *   **局部检索 (Local Search)**：从查询实体出发，沿图边遍历关联实体和文档。
    *   **全局检索 (Global Search)**：在社区摘要层面进行检索，适合需要全局概览的问题。

### 三、 知识库文档更新策略

#### 1. 核心挑战
*   **增量更新 vs 全量重建**：新增文档如何入库？修改过的文档如何更新向量？
*   **版本控制**：同一文档的新旧版本如何管理？是否需要保留历史版本？
*   **去重**：如何避免相同内容的文档被重复索引？

#### 2. 更新策略
*   **增量更新**：
    *   通过文档哈希（MD5/SHA256）判断文档是否变化。
    *   变化的文档重新解析、分块、向量化，替换旧向量。
    *   未变化的文档跳过。
*   **版本控制**：
    *   每次更新保留文档版本号和时间戳。
    *   检索时可选择只搜索最新版本，或在特定时间点做快照检索。
*   **去重**：
    *   基于文档指纹（内容哈希）去重。
    *   基于向量相似度去重（如果两个 Chunk 的向量余弦相似度 > 0.95，认为是重复内容）。
*   **全量重建**：
    *   当 Embedding 模型更换或 Chunk 策略调整时，需要对整个知识库全量重建索引。
    *   建议采用蓝绿部署：新索引构建完成后，原子切换。
