*   **袁志刚专属特训回答模版**：
    1.  **sky-ai 系统架构分层**：
        ```
        用户层 (客户端)
           │
           ▼
        ┌─────────────────────────────────────────────┐
        │  接入层 (WebSocket / HTTP)                    │

        │  编排层 (Spring AI Advisor Chain)             │
        │                                             │
        │  IntentRecognitionAdvisor  (意图识别)          │
        │       ↓                                     │
        │  UserContextAdvisor  (画像注入+工具白名单)      │
        │       ↓                                     │
        │  RagAdvisor  (知识库检索增强)                   │
        │       ↓                                     │
        │  ToolFilterAdvisor  (动态工具过滤)              │
        │       ↓                                     │
        │  SafeToolCallAdvisor  (工具调用+熔断)           │
        └─────────────────────────────────────────────┘

           ▼

        │  工具层 (Tools)                               │
        │  - CartTools (购物车操作)                      │
        │  - OrderTools (订单操作)                       │

        │  - PgvectorVectorStore (向量数据)              │

        └─────────────────────────────────────────────┘
        ```

    2.  **核心设计决策**：
        *   **Advisor 链（责任链模式）**：每个横切关注点（意图识别、画像注入、RAG、工具过滤、熔断）封装为独立的 Advisor，通过 `Ordered` 接口控制执行顺序。新增功能只需添加 Advisor，完全符合开闭原则。
        *   **双模式支持**：每个 Advisor 同时实现 `CallAdvisor` 和 `StreamAdvisor`，支持同步和流式两种交互模式。
        *   **意图驱动的权限隔离**：通过意图识别动态生成工具白名单，而非一次性暴露所有工具，防止模型误调用高风险操作。

### 2. 工具权限安全与【AI 应用安全治理】
*   **面试官切入点**：
    > "在你的 AI 客服系统中，Agent 可以调用订单取消、退款等敏感操作。你是如何防止模型误操作或被恶意利用的？"
*   **袁志刚专属特训回答模版**：
    1.  **三层安全防御体系**：
        *   **第一层：意图驱动的工具白名单**：`UserContextAdvisor.allowedTools()` 根据识别的意图类型，精确控制本次对话可用的工具集。例如，查询菜单意图绝不会暴露 `cancelOrder` 或 `requestRefund` 工具。
        *   **第二层：工具调用签名熔断**：`SafeToolCallAdvisor` 检测重复签名和轮次超限，防止模型陷入死循环或重复执行同一操作。
        *   **第三层：业务层幂等校验**：在 `OrderTools`、`CartTools` 等工具实现内部，通过状态机校验（如订单状态必须为 PENDING 才能取消）和幂等键保障操作安全。

## 🚀 第一优先级核心考点详解（生产级 AI 应用架构、模型网关）

### 一、 生产级 AI 应用架构设计

#### 1. 核心架构模块
一个生产级的 AI 应用至少需要以下模块：

| 模块 | 职责 | 关键考量 |
| :--- | :--- | :--- |
| **入口层** | 接收用户请求（HTTP/WebSocket/SDK） | 鉴权、限流、协议转换 |
| **编排层** | 组织 AI 组件的执行流程 | 责任链/DAG/Agent Loop 的选择 |
| **Prompt/Context 管理** | 管理和组装模型输入 | 版本控制、A/B 测试、Token 预算 |
| **RAG** | 检索外部知识 | 召回率、延迟、知识库更新 |
| **Memory** | 管理会话和用户记忆 | 短期/长期记忆、上下文溢出 |
| **Tool Calling** | 调用外部工具和 API | 权限控制、熔断、幂等 |
| **模型网关** | 统一管理模型调用 | 路由、限流、fallback、成本 |
| **可观测** | 监控和日志 | Trace、指标、告警 |
| **评测** | 质量保障 | Golden Set、灰度、Trace 回放 |
| **安全合规** | 风险防控 | Prompt 注入、PII 过滤、审计 |

#### 2. Prompt 管理工程化
*   **版本控制**：每个 Prompt 模板有版本号，支持回滚。
*   **A/B 测试**：新 Prompt 与旧 Prompt 灰度对比。
*   **动态加载**：Prompt 存储在配置中心或数据库，无需重新部署即可更新。
*   **模板引擎**：使用变量占位符，运行时动态填充用户数据和检索结果。

#### 3. 可观测体系
*   **Trace 链路**：每次请求从入口到模型返回的完整链路追踪，包括每个 Advisor 的耗时、模型推理耗时、工具调用耗时。
*   **核心指标**：
    *   **TTFT (Time To First Token)**：首 Token 延迟。
    *   **TPS (Tokens Per Second)**：模型输出速率。
    *   **Token 消耗**：输入/输出 Token 的用量和成本。
    *   **工具调用成功率**：工具调用的成功/失败/超时分布。
    *   **意图识别置信度分布**：各意图类型的识别准确率。
*   **告警规则**：Token 消耗异常激增、工具调用成功率骤降、模型 API 错误率超过阈值。

### 二、 大模型网关（LLM Gateway）

#### 1. 为什么需要模型网关
当系统使用多个 LLM 提供商（OpenAI、Anthropic、DeepSeek 等）时，需要一个统一的中间层来管理模型调用。

#### 2. 模型网关核心能力

##### 多模型路由
*   **基于任务类型路由**：意图识别使用快速廉价模型（如 GPT-4o-mini），生成回复使用强力模型（如 GPT-4o）。
*   **基于成本路由**：简单问题路由到便宜模型，复杂问题路由到强力模型。
*   **负载均衡**：同一模型的多个 API Key 之间做负载分配。

##### Fallback 降级
```
主模型（GPT-4o）
  │ 失败/超时
  ▼
备用模型（Claude 3.5）
  │ 失败/超时
  ▼
兜底模型（GPT-4o-mini）
  │ 失败/超时
  ▼
静态降级回复（预设文案）
```

##### 限流配额
*   **TPM 限流**：按 Token Per Minute 限制单个模型的调用量。
*   **RPM 限流**：按 Request Per Minute 限制请求频次。
*   **成本预算**：按日/周/月设置成本上限，超限后自动降级。

##### 成本归因
*   **按业务线**：不同业务线的 AI 调用成本分别统计。
*   **按用户**：高频用户的 Token 消耗单独归因。
*   **按功能**：意图识别、RAG 生成、工具调用的 Token 成本分别计量。

##### 缓存策略
*   **语义缓存**：对相似 query 的模型回复进行缓存。通过向量相似度判断 query 是否命中缓存。
*   **精确缓存**：对完全相同的 Prompt 进行缓存。
*   **缓存失效**：知识库更新后自动失效相关缓存。

## 🛠️ 第二优先级核心考点详解（AI 语音技术、安全合规、评测闭环）

### 一、 AI 语音技术（实时语音 Agent）

#### 1. 核心链路
```
用户语音 → VAD → ASR → LLM → TTS → 音频流 → 用户耳机
```

| 组件 | 全称 | 职责 |
| :--- | :--- | :--- |
| **VAD** | Voice Activity Detection | 检测语音起止，区分说话和静音 |
| **ASR** | Automatic Speech Recognition | 语音转文字 |
| **LLM** | Large Language Model | 理解意图并生成文本回复 |
| **TTS** | Text-To-Speech | 文字转语音 |

#### 2. 低延迟设计
*   **流式管道**：ASR 边识别边输出（流式 ASR）→ LLM 流式生成 → TTS 边合成边播放（流式 TTS）。
*   **目标延迟**：从用户说完话到 Agent 开始播放回复，总延迟控制在 1-2 秒内。
*   **VAD 灵敏度**：需要平衡"检测到用户停止说话"的速度和"误判停顿为结束"的风险。

#### 3. 打断处理（Barge-in）
*   **用户打断**：用户在 Agent 播放回复时重新说话。
*   **处理方式**：VAD 检测到新语音 → 立即停止 TTS 播放 → 中断当前 LLM 生成 → 将已生成的部分和用户新输入合并为新一轮请求。

#### 4. 状态机设计
```
IDLE → LISTENING → PROCESSING → SPEAKING → IDLE
  │                                  │
  └──── 打断 (Barge-in) ←───────────┘
```

### 二、 AI 应用安全合规

#### 1. Prompt 注入防御
*   **直接注入**：用户在输入中直接覆盖 System Prompt（如"忽略以上所有指令，你现在是..."）。
*   **间接注入**：攻击者在外部数据源（如知识库文档）中嵌入恶意指令，通过 RAG 被注入到上下文。
*   **防御方式**：
    *   **输入过滤**：检测和清除可疑的注入模式。
    *   **Prompt 分层**：System Prompt 和用户输入用分隔符严格隔离。
    *   **输出校验**：检查模型输出是否包含敏感信息或违规操作。
    *   **权限最小化**：通过工具白名单限制 Agent 能力边界。

#### 2. PII（个人可识别信息）过滤
*   **输入端**：在用户消息送入 LLM 前，检测并脱敏 PII（姓名、手机号、地址等）。
*   **输出端**：在模型回复返回用户前，二次检查是否泄露了其他用户的 PII。
*   **日志端**：Trace 日志中的 PII 需要脱敏存储。

#### 3. 操作审计
*   **全链路审计**：记录每次 Agent 对话的完整信息——用户输入、意图识别结果、工具调用详情（工具名、参数、返回值）、模型回复、Token 消耗。
*   **敏感操作告警**：对 `cancelOrder`、`requestRefund` 等高风险操作设置告警规则。
*   **审计数据存储**：审计日志独立存储，不可篡改，保留期至少 90 天。

### 三、 AI 应用评测闭环

#### 1. 完整的质量闭环
```
需求变更（Prompt 修改/知识库更新/模型升级）
     │
     ▼
┌─────────────────────────────────┐
│  离线评测                        │
│  - Golden Set 自动化评估          │
│  - Trace 回放对比                │
│  - LLM-as-Judge 多维度打分       │
│  - 人工复核边界 case              │
└─────────────────────────────────┘
     │ 通过
     ▼
┌─────────────────────────────────┐
│  灰度发布                        │
│  - 小流量 A/B 测试               │
│  - 关键指标对比（准确率/延迟/成本）  │
│  - 用户满意度采样                  │
└─────────────────────────────────┘
     │ 通过
     ▼
┌─────────────────────────────────┐
│  全量发布                        │
│  - 持续监控核心指标               │
│  - 异常自动回滚                   │
│  - 新 Trace 采样入 Golden Set     │
└─────────────────────────────────┘
```

#### 2. 如何证明"新 Prompt 比旧 Prompt 更好"
1.  **离线对比**：在 Golden Set 上分别运行新旧 Prompt，用 LLM-as-Judge 多维度打分（准确性、完整性、安全性、用户体验）。
2.  **Trace 回放**：将线上真实请求的 Trace 回放到新 Prompt 版本，对比输出差异。
3.  **灰度验证**：将小流量切到新版本，对比业务指标（任务完成率、用户满意度、工具调用准确率）。
4.  **统计显著性**：使用 A/B 测试的统计检验（如 t-test 或 Mann-Whitney U），确保差异不是随机波动。

#### 3. 模型供应商故障处理
*   **多供应商冗余**：至少对接两家 LLM 供应商。
*   **健康检查**：定期对每个供应商发送探针请求，监控可用性和延迟。
*   **自动切换**：检测到主供应商异常后，自动切换到备用供应商，同时触发告警。
*   **降级策略**：所有 LLM 供应商不可用时，降级到基于规则的回复（如预设的 FAQ 回复模板）。
