## 🎯 简历亮点深度关联与大厂面试预测

### 1. Spring AI 流式响应与【Token 机制及流式输出工程】
*   **面试官切入点**：
    > "你的 AI Agent 管道中，每个 Advisor 都同时实现了 `CallAdvisor` 和 `StreamAdvisor` 双接口。请问流式输出（Streaming）在大模型中的底层原理是什么？它和一次性返回有什么区别？你在实际项目中是如何处理流式响应的？"
*   **袁志刚专属特训回答模版**：
    1.  **流式输出底层原理**：大模型的推理过程是**逐 Token 生成**的（自回归解码）。每生成一个 Token，都要将之前所有的 Token 重新输入模型计算 Attention，然后输出下一个 Token 的概率分布。流式输出就是让服务端每生成一个或几个 Token 就立即通过 **SSE（Server-Sent Events）** 推送给客户端，而非等所有 Token 生成完毕再一次性返回。
    2.  **在 sky-ai 中的硬核落地**：我们的每个 Advisor（如 `UserContextAdvisor`、`IntentRecognitionAdvisor`、`RagAdvisor`、`ToolFilterAdvisor`）都实现了 `StreamAdvisor` 接口，其 `adviseStream()` 方法返回 **`Flux<ChatClientResponse>`**——这是 Reactor 响应式流。当客户端通过 WebSocket 连接时，消息以流式逐帧推送到前端，首字延迟从秒级降低到毫秒级，极大提升了用户的交互体验。
    3.  **流式 vs 非流式的工程取舍**：
        *   **流式优势**：首字延迟低（Time To First Token, TTFT 可降至 200ms 以下）、用户感知流畅。
        *   **流式挑战**：无法在返回前对完整响应做校验（如 JSON 格式校验、敏感词过滤）。我们的 `SafeToolCallAdvisor` 需要等拿到完整的 `ChatClientResponse` 后才能进行工具调用签名检测和熔断。

### 2. 意图识别 LLM 调用与【结构化输出工程】
*   **面试官切入点**：
    > "你的意图识别模块是通过 LLM 进行的，它需要返回一个包含意图类型、置信度、实体列表等字段的结构化结果。你是如何保证 LLM 输出格式稳定可靠的？"
*   **袁志刚专属特训回答模版**：
    1.  **结构化输出的三种方案对比**：
        *   **纯 Prompt 约束**（最弱）：在 System Prompt 中写"请以 JSON 格式输出"。但 LLM 可能输出多余文字、丢失字段、格式不合法。**生产环境绝不能依赖此方案**。
        *   **JSON Mode**（中等）：模型 API 开启 `response_format: { type: "json_object" }`。保证返回合法 JSON，但不保证 schema 正确（可能多字段或少字段）。
        *   **Function Calling / Tool Calling**（最强）：通过 JSON Schema 严格定义输出结构。模型被约束为只能按照预定义的函数签名返回结果。
    2.  **在 sky-ai 中的实践**：我们的 `CustomerIntentRecognitionService` 利用 Spring AI 的 Function Calling 能力，将 `IntentRecognitionResult`（含 `IntentType intent`、`ConfidenceLevel confidence`、`Map<String, String> entities`、`List<IntentType> candidateIntents` 等字段）定义为结构化输出 Schema。LLM 被约束为必须按此 Schema 返回，解析后直接映射为 Java 对象，无需手动做 JSON 解析和异常处理。
    3.  **服务端兜底校验**：即使使用了 Function Calling，生产中仍需在服务端做额外校验——如枚举值是否合法（`IntentType.fromValue()`）、必填字段是否为空、置信度是否在有效范围内。我们在 `IntentRecognitionAdvisor` 中对 `null` 结果做了兜底：`result = new IntentRecognitionResult(IntentType.OTHER, ConfidenceLevel.LOW, Map.of(), List.of(), null, false, null)`。

## 🚀 第一优先级核心考点详解（Token 机制、上下文窗口、采样参数、幻觉）

### 一、 Token 机制底层原理
Token 是大模型处理文本的最小单元，是介于"字符"和"词"之间的粒度。

1.  **分词算法**：主流 LLM 使用 **BPE (Byte-Pair Encoding)** 或其变体进行分词。它通过统计语料中高频出现的字节/字符组合，将常见子词合并为一个 Token。
2.  **不同文本的 Token 消耗差异**：
    *   **英文**：一个 Token 平均覆盖 4 个字符（约 3/4 个单词）。
    *   **中文**：一个汉字通常被编码为 1-2 个 Token（因为中文字符在 BPE 词表中的覆盖率不如英文）。
    *   **代码**：关键字通常是独立 Token，变量名可能被拆分。
3.  **Token 计费模型**：大模型 API 按 **输入 Token + 输出 Token** 分别计费，且输出 Token 单价通常是输入的 2-4 倍。在生产环境中控制 Token 消耗直接影响成本。

### 二、 上下文窗口（Context Window）
上下文窗口是模型单次请求能处理的 **Token 总量上限**（输入 + 输出 Token 之和）。

1.  **典型模型上下文长度**：
    *   GPT-4o：128K Token
    *   Claude 3.5 Sonnet：200K Token
    *   DeepSeek V3：128K Token
2.  **长上下文不一定更好**：
    *   **"迷失在中间"问题 (Lost in the Middle)**：研究表明，模型对上下文窗口的**开头和结尾**关注度远高于中间部分。在 RAG 场景中，将最相关的检索结果放在上下文首部或尾部效果更好。
    *   **推理延迟**：上下文越长，Attention 计算量呈 O(n²) 增长（标准 Self-Attention），推理延迟和成本显著上升。
    *   **Token 预算管理**：在我们的 sky-ai 系统中，`UserContextAdvisor` 通过 `ProfileInjectionLevel`（NONE/SUMMARY/FULL）动态控制注入的用户记忆量，避免在简单意图（如查店铺状态）下浪费 Token 预算。

### 三、 采样参数调优（Temperature、Top-P、Top-K）
这三个参数控制模型从候选 Token 概率分布中"如何选择下一个 Token"。

1.  **Temperature（温度）**：
    *   控制概率分布的"尖锐/平坦"程度。值越低（→0），分布越集中在最高概率 Token，输出越确定；值越高（→2），分布越均匀，输出越随机/有创意。
    *   **生产调优**：意图识别、分类任务设为 0-0.3（要求确定性）；创意文案设为 0.7-1.0。
2.  **Top-P（核采样）**：
    *   只保留概率累积和达到 P 的最小 Token 集合，从中随机采样。Top-P=0.1 表示只从累积概率前 10% 的 Token 中选择。
    *   **与 Temperature 互斥**：通常只调一个，另一个设为 1.0。
3.  **Top-K**：
    *   只保留概率最高的 K 个 Token，从中采样。Top-K=1 等价于贪婪解码（始终选最高概率 Token）。

### 四、 大模型幻觉（Hallucination）
幻觉是指模型生成**看似合理但事实上错误或不存在**的内容。

1.  **幻觉类型**：
    *   **事实性幻觉**：编造不存在的事实、数据、引用。
    *   **忠实性幻觉**：与给定上下文不一致的输出（RAG 场景下最致命——检索到了正确证据但生成了错误答案）。
2.  **工程缓解方式**：
    *   **RAG 检索增强**：将事实依据通过检索注入上下文，减少模型"凭空编造"。
    *   **低 Temperature**：降低随机性，让模型更倾向于高置信度输出。
    *   **结构化输出约束**：通过 Function Calling / JSON Schema 约束输出格式，减少自由发挥空间。
    *   **后置校验**：在模型输出后进行事实核查（如搜索引擎验证、知识库对照）。
    *   **引用标注**：要求模型标注信息来源，方便人工审核。

## 🛠️ 第二优先级核心考点详解（API 调用工程、Function Calling、评测体系）

### 一、 大模型 API 调用工程实践

#### 1. Prompt 组装与消息角色
大模型 API 接收的是**结构化消息列表**，每条消息有明确角色：
*   **System**：设定模型行为规范和角色设定（不参与用户交互）。
*   **User**：用户输入。
*   **Assistant**：模型回复。
*   **Tool/Function**：工具调用的结果返回。

在 sky-ai 中，`UserContextAdvisor` 通过 `instructions.add(0, new SystemMessage(contextBlock))` 在首位织入用户画像上下文，`RagAdvisor` 通过 `instructions.add(0, new SystemMessage(RETRIEVAL_CONTEXT_PREFIX + retrievalResult.context()))` 在首位织入检索上下文。

#### 2. 生产级 API 调用链路设计
*   **重试机制**：模型 API 可能因限流（429）、超时（504）、服务不可用（503）而失败。需要实现指数退避重试（Exponential Backoff）。
*   **限流配额**：大模型 API 通常有 TPM（Token Per Minute）和 RPM（Request Per Minute）限制。需要在调用端实现令牌桶或滑动窗口限流。
*   **降级策略**：主模型不可用时，自动切换到备用模型（如 GPT-4o 降级到 GPT-4o-mini）。
*   **超时控制**：流式输出设置首 Token 超时（TTFT Timeout）和总超时；非流式设置请求级超时。
*   **幂等性保障**：对于写操作类的工具调用（如下单、取消订单），需要确保重试不会导致重复执行。

### 二、 Function Calling / Tool Calling 底层链路

#### 1. 核心概念区分
| 概念 | 定义 | 执行方 |
| :--- | :--- | :--- |
| **Function Calling** | 模型决定调用哪个函数及参数，但不执行函数 | 模型决策，客户端执行 |
| **Tool Calling** | Function Calling 的超集，支持多个工具并行调用 | 模型决策，客户端执行 |
| **MCP (Model Context Protocol)** | 标准化的工具注册与调用协议，解决工具接入碎片化 | 模型决策，MCP Server 执行 |

#### 2. Function Calling 的请求-响应循环
1.  客户端将用户消息 + 可用函数声明（JSON Schema）发送给模型。
2.  模型分析用户意图，决定是否调用函数。如果决定调用，返回函数名 + JSON 格式参数。
3.  客户端解析返回值，调用实际函数，获取函数执行结果。
4.  客户端将函数结果以 Tool 角色消息回传给模型。
5.  模型基于函数结果生成最终回复。

#### 3. 在 sky-ai 中的实践
*   `ToolFilterAdvisor` 从 `DynamicToolCallbackRegistry` 中根据白名单动态筛选 `ToolCallback` 列表，并通过 `ToolCallingChatOptions.setToolCallbacks()` 注入到 Prompt 选项中。
*   `SafeToolCallAdvisor` 继承 `ToolCallAdvisor`，在每轮工具调用后通过 `guard()` 方法检测签名重复和轮次超限（`MAX_TOOL_CALL_ROUNDS = 4`），防止 Agent 陷入死循环。

### 三、 AI 应用评测体系

#### 1. 评测为什么重要
AI 应用不像传统软件可以用确定性测试覆盖。模型输出本质上是概率性的，每次调用可能产生不同结果。需要一套系统化的评测机制来量化和保障输出质量。

#### 2. 评测方法论

| 评测方法 | 适用阶段 | 核心思路 |
| :--- | :--- | :--- |
| **Golden Set** | 离线评测 | 人工标注标准答案集，用自动化指标（BLEU、ROUGE、F1）评估 |
| **LLM-as-Judge** | 离线/在线 | 用另一个 LLM 当裁判，按维度打分（准确性、完整性、安全性） |
| **Trace 回放** | 回归评测 | 录制线上真实请求，回放到新版本对比输出差异 |
| **线上灰度** | 发布验证 | A/B 测试，将小流量切到新版本，对比关键指标 |
| **人工复核** | 质量兜底 | 随机抽样 + 边界 case 人工审核 |

#### 3. RAG 和 Agent 专项评测指标
*   **RAG 指标**：
    *   **召回率 (Recall)**：正确文档是否被检索到。
    *   **准确率 (Precision)**：检索到的文档中有多少是相关的。
    *   **忠实度 (Faithfulness)**：生成的答案是否忠实于检索到的上下文。
    *   **答案相关性 (Answer Relevancy)**：生成的答案是否回答了用户的问题。
*   **Agent 指标**：
    *   **任务完成率**：Agent 是否最终完成了用户意图。
    *   **工具调用准确率**：Agent 是否调用了正确的工具、传了正确的参数。
    *   **步数效率**：完成任务用了多少步（越少越好）。
    *   **安全合规率**：Agent 是否触发了敏感操作或越权行为。
