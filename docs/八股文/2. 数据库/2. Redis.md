## 🎯 简历亮点深度关联与大厂面试预测

### 1. Caffeine + Redis 二级缓存与【缓存击穿、穿透核心生产级设计】
*   **面试官切入点**：
    > “在黑马点评中，你构建了多级缓存抗压架构。面对高并发压测，如果遭遇恶意的缓存穿透（如查询不存在的店铺）或突发的热点缓存击穿（如商铺缓存到期的一瞬间有十万并发涌入），你是如何保证数据库不崩溃的？‘逻辑过期’为什么能实现无锁、低延迟防击穿？”
*   **袁志刚专属特训回答模版**：
    1.  **缓存穿透（空值缓存强防御）**：面对查询不存在商铺的恶意流量，我们在本地二级缓存和 Redis 一级缓存中均开启了**空值缓存策略**：一旦数据库查询返回 `null`，我们就向缓存中写入一个标识空对象 `""`，并设置一个极短的过期时间（如 2 分钟）。这能确保后续重复的穿透流量在缓存层被直接拦截，不再打到数据库。
    2.  **缓存击穿之痛（传统互斥锁的局限）**：传统防击穿使用互斥锁（如 Redis `SETNX`）。当缓存失效时，只有一个线程能拿到锁去重建缓存，其他成千上万个线程必须在 Java 端循环自旋等待，导致系统平均延迟飙升，吞吐量锐减。
    3.  **优雅的逻辑过期方案（无锁、零延迟）**：
        *   **设计思想**：我们在存入 Redis 的商铺 JSON 数据中，额外包裹一个逻辑过期时间字段（`expireTime = 当前时间 + 30分钟`），但在 Redis 物理上**永远设置永久不过期**。
        *   **读写流转机制**：当高并发查询该商铺时，线程读取 Redis 发现当前系统时间已超过逻辑过期时间。此时，该线程不进行自旋等待，而是**立即获取一个互斥锁 `lock`**。
        *   **异步重建与旧值兜底**：抢到锁的线程，直接利用 Java 线程池**异步开启一个后台线程去查询数据库并重建缓存**。而该线程（以及抢锁失败的所有其他并发线程）**完全不等待，直接返回旧的过期数据**。这彻底实现了读写分离，消除了高并发抢锁和自旋等待，使得压测下核心接口响应延迟始终保持在极低的毫秒级。

### 2. 秒杀库存预扣减与【Redis + Lua 脚本原子性校验】
*   **面试官切入点**：
    > “在高并发秒杀中，你是如何防止超卖和保障‘一人一单’的？为什么必须要用 Redis + Lua 脚本？普通的 Redis 事务或者 Java 加锁行不行？”
*   **袁志刚专属特训回答模版**：
    1.  **一人一单的并发并发痛点**：秒杀扣减库存前，必须先校验当前用户是否已下过单。这包含两步：`GET user_order_status` 和 `DECR stock`。如果这两步由 Java 业务层分别发给 Redis，在并发瞬时涌入时，由于**两步操作非原子性**，线程 A 和线程 B 同时查到该用户没有下单，然后同时去扣减库存，就会发生“超卖”和“一人多单”。
    2.  **Java 加锁的弊端**：在 JVM 内存层加 `ReentrantLock` 只能对单机有效，在分布式部署下完全失效。而在分布式环境下用悲观锁性能太低，无法抗住秒杀的吞吐量。
    3.  **Redis + Lua 脚本的单线程原子底座**：
        *   **原子保障**：Redis 底层采用**单线程执行模型**。我们将“校验一人一单（查询用户购买记录是否存在）”和“库存预扣减（判断 stock 是否大于 0 并扣减）”这两步逻辑全部写入 Lua 脚本中。
        *   **插队禁止**：当我们将 Lua 脚本发给 Redis 执行时，Redis 会将整个脚本作为一个**不可分割的整体**执行。在此期间，任何其他客户端提交的读写命令都无法插队。这完美保障了“多步操作的内存级强原子性”，高并发高吞吐下也绝不会多出任何一张脏单。

### 3. Redisson 分布式锁与【可重入与看门狗底层原理】
*   **面试官切入点**：
    > “你在黑马点评中用到了 Redisson 分布式锁进行并发兜底。请问普通的 `setnx` 实现分布式锁有什么重大缺陷？Redisson 的锁底层使用的是什么数据结构？它的‘看门狗 (Watch Dog)’机制和‘可重入’是如何实现的？”
*   **袁志刚专属特训回答模版**：
    1.  **普通 setnx 锁的死锁大坑**：普通的 `setnx key value` 配合 `expire` 存在两大痛点：一是加锁和设置过期时间非原子操作，中途挂机易死锁；二是业务执行超时，锁提前过期释放，引发并发竞争。
    2.  **Redisson Hash 锁结构与可重入底层**：
        *   Redisson 弃用 String 结构，在底层使用 Redis 的 **Hash 结构** 来存储锁。
        *   **Hash 结构设计**：`Key` 是锁的名称，`Field` 是当前持有锁的 `UUID + 线程ID`，`Value` 是**锁的重入次数（Counter）**。
        *   **可重入 Lua 实现**：当同一个线程再次尝试获取这把锁时，底层 Lua 脚本检测到 Hash 里的 Field 与自己一致，不会报错，而是直接把对应的 `Value` 计数器 `+1`。释放锁时计数器 `-1`，直到计数器归零，直接调用 `DEL` 删除该 Key，彻底释放锁。这完美契合了 Java `ReentrantLock` 的可重入思想。
    3.  **看门狗 (Watch Dog) 自动续期原理**：
        *   当线程成功获取锁且没有指定释放时间时（默认生存时间为 30s），Redisson 会启动一个后台定时任务线程——**看门狗 (Watch Dog)**。
        *   只要当前持有锁的线程未执行完毕，看门狗会每隔 **10s**（生存时间的 1/3）自动向 Redis 发送一段 Lua 脚本，将该锁的生存时间**重新重置为 30s**。
        *   如果业务线程中途卡死，或者 JVM 异常崩溃，看门狗线程也会随之销毁。锁在达到剩余过期时间后会自动过期释放，杜绝了无期限死锁发生。

### 4. 延迟订单处理与【Redis ZSet 延迟队列机制】
*   **面试官切入点**：
    > “你提到引入 Redis 延迟队列，将高耗时的订单超时处理与核心支付链路异步解耦。请问你是如何使用 Redis 实现延迟队列的？”
*   **袁志刚专属特训回答模版**：
    1.  **ZSet 结构与超时分数映射**：我们利用 Redis 的 **ZSet (有序集合)** 结构。我们将“订单超时取消任务”作为 ZSet 的 Value，将“订单超时的时间戳”作为 **Score (分数)**。
    2.  **定时轮询消费**：我们通过后台线程池，以单线程或多线程定时轮询 Redis 的 ZSet。通过命令 `ZRANGEBYSCORE key 0 <当前系统时间戳> LIMIT 0 1` 获取当前已经过期且待执行的超时订单任务。
    3.  **原子弹出与防重复执行**：获取任务后，为了防止在多节点集群部署下发生重复消费，我们通过 Lua 脚本执行 `ZREM` 将其原子性弹出。只有成功移除当前成员的节点，才能真正去执行“更新数据库订单状态为已取消”的业务。

## 🚀 第一优先级核心考点详解（单线程多路复用、常用数据结构底层、双写一致性）

### 一、 Redis 为什么这么快？（单线程模型与 I/O 多路复用）
Redis 的读写吞吐量能够轻松达到 10w+ QPS，其核心秘诀归功于以下三点：

1.  **纯内存操作**：所有读写操作均在内存中完成，没有任何随机磁盘 I/O 的阻塞。
2.  **高效的数据结构**：底层有跳表、压缩列表等专门优化过的高性能算法支撑。
3.  **单线程模型 + I/O 多路复用**：
    *   **避免线程切换损耗**：采用单线程模型来处理所有的网络请求和键值读写。这彻底避免了多线程环境下昂贵的“线程上下文切换”损耗，也完全规避了各种复杂的并发锁竞争。
    *   **I/O 多路复用模型 (基于 epoll)**：Redis 采用非阻塞的 I/O 多路复用机制。它通过单线程并发监听成千上万个网络连接套接字（Socket）。一旦某个 Socket 准备好了读写事件，就会通过**事件派发器 (Event Dispatcher)** 将其放入一个单线程任务队列中，由 Redis 主线程依次处理。这使得单线程也能撑起海量客户端的并发连接。

### 二、 Redis 常用数据结构及其底层实现（面试重头戏）

#### 1. String 的底层：SDS (简单动态字符串)
Java 中的 String 底层是 char 数组，而 Redis 弃用 C 语言原生以 `\0` 结尾的字符数组，设计了 **SDS** 结构：
*   **结构**：包含 `len`（已用长度）、`alloc`（已分配内存容量）、`flags`（SDS类型）和 `buf[]`（真实字符数组）。
*   **SDS 的革命性优势**：
    1.  **O(1) 复杂度获取长度**：直接读取 `len` 变量，而 C 语言必须 $O(N)$ 遍历数组。
    2.  **杜绝缓冲区溢出**：拼接字符前，SDS 会自动检测并动态扩容，防止覆写其他内存。
    3.  **减少内存分配次数（空间预分配与惰性释放）**：扩容时会多分配一倍的空间作为冗余；缩短时并不立即释放内存，仅修改 `len` 长度，以便下次直接复用。
    4.  **二进制安全**：以 `len` 决定字符串终点，允许存储包含 `\0` 的任意二进制数据（如图片、视频字节流）。

#### 2. ZSet 的底层：跳表 (SkipList) 与压缩列表 (ZipList)
*   当元素数量较少时，ZSet 底层采用 **ZipList (压缩列表)** 以节省内存空间。
*   当数据量变大（默认大于 128 个或值长度大于 64 字节）时，自动转为 **SkipList (跳表)**。
*   **跳表底层原理**：
    *   跳表是一种**多层级的链表结构**。它在普通双向链表之上，构建了多层“稀疏索引”节点。
    *   **检索时间复杂度为 $O(\log N)$**：查找时从顶层索引开始横向跨越，定位后下降一层继续，类似于二分查找，检索极其高效。

### 三、 Redis 与数据库的双写一致性最佳实践
在大流量高并发下，保证 Redis 缓存和 MySQL 数据库中数据绝对一致是经典的系统设计考点。

1.  **大厂首选方案：先更新数据库，再删除缓存**：
    *   *为什么是删除而不是更新？*：更新缓存容易导致并发覆盖冲突（且如果缓存计算复杂，频繁更新得不偿失，删除属于惰性加载思想）。
    *   *可能存在的极端不一致情况*：缓存刚好失效。线程 A 读缓存未命中，去读数据库拿到旧值 `10`。此时线程 B 更新数据库为 `20`，并删除缓存。接着线程 A 慢一步将旧值 `10` 写入缓存，导致脏数据。
    *   *概率分析*：极低。因为写入缓存的随机内存操作速度远比写数据库磁盘操作快得多，线程 A 几乎不可能比线程 B 的写库和删缓存还慢。
2.  **兜底保障：延迟双删机制**：
    *   为了彻底消灭上述极低概率的不一致，我们可以在线程 B 更新完数据库并删除缓存后，**让当前线程 sleep 500ms，再次执行一次删除缓存**。这能确保在写库期间所有被其他读线程误写入的脏缓存都能被第二次干净清理。
3.  **终极解耦：基于 Canal 监听 Binlog 异步清理**：
    *   业务代码只管写 MySQL。我们通过部署 **Canal 中间件**，将 Canal 伪装成 MySQL 的从库，实时订阅并解析 MySQL 的 **Binlog (二进制归档日志)**。一旦发现商铺数据发生变化，由 Canal 异步发送 MQ 消息触发缓存清理，彻底实现业务解耦与强最终一致性。

## 🛠️ 第二优先级核心考点详解（持久化、过期淘汰）

### 一、 Redis 两种持久化机制深度对比
Redis 是内存数据库，为了防止服务器断电导致数据全部丢失，必须将数据保存到磁盘上。

1.  **RDB (Redis Database 快照)**：
    *   **原理**：在指定的时间间隔内，将内存中的全量数据以二机制压缩文件的形式（`dump.rdb`）写入磁盘（通过 `fork` 子进程利用 **Copy-On-Write 写时复制** 进行后台写盘，不阻塞主线程）。
    *   **优点**：文件体积极小，灾难恢复速度极快，适合做全量定期冷备。
    *   **缺点**：实时性极低。如果突然断电，会丢失最后一次快照之后的全部数据。
2.  **AOF (Append Only File 增量追加)**：
    *   **原理**：实时将每一条写命令通过 `write` 写入系统缓冲区，并由配置（默认 `everysec` 每秒）强制 `fsync` 刷入磁盘的 `appendonly.aof` 文件中。
    *   **优点**：数据安全性极高，几乎不丢数据。
    *   **缺点**：文件体积庞大，随着写命令堆积，恢复速度极慢（需要重新执行一遍所有命令）。
3.  **大厂最佳实践：混合持久化 (Hybrid)**：
    *   从 Redis 4.0 开始，官方推出混合持久化模式。在 AOF 重写时，先将内存中的全量快照以 **RDB 格式** 写入 AOF 文件头部，随后新接收的写命令继续以 **AOF 文本格式** 追加到尾部。这兼具了 RDB 的快速恢复和 AOF 的高数据安全性。

### 二、 Redis 过期删除与内存淘汰策略

#### 1. 过期删除策略（Key 到期了怎么删？）
Redis 采用 **惰性删除** + **定期删除** 双剑合璧的方式，在 CPU 消耗和内存占用之间达到平衡。
1.  **惰性删除**：当 Key 过期时，不去管它。只有当客户端**再次访问该 Key 时**，Redis 会先检测其是否过期，若过期则删除并返回空。
    *   *缺点*：如果大量 Key 过期后永远不再被访问，会持续占满内存，发生内存泄露。
2.  **定期删除**：Redis 每隔 100ms 随机抽取一部分设置了过期时间的 Key，检测并清理其中已过期的 Key。

#### 2. 内存淘汰策略（内存写满了怎么办？）
当 Redis 的运行内存超过 `maxmemory` 上限时，会触发**内存淘汰策略**。
*   **LRU (Least Recently Used)**：淘汰**最近最久未使用**的 Key。
*   **LFU (Least Frequently Used)**：淘汰**使用频次最低**的 Key（能更精准地保留高频热点商铺，防止冷门数据突发一次性访问干扰 LRU 判定）。
*   **大厂高频选项**：
    *   `volatile-lru` / `volatile-lfu`：仅从**设置了过期时间**的键中，挑选 LRU/LFU 淘汰。
    *   `allkeys-lru` / `allkeys-lfu`：从**所有键**中，挑选 LRU/LFU 淘汰（常作为缓存服务的首选配置）。
