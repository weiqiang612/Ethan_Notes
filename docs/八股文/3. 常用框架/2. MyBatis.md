## 🔑 前置基础概念速查（必读，5 分钟建立认知底座）

在深入映射底层之前，先把下面这几个概念理解清楚，后文所有分析都建立在这些基础上。

| 概念 | 一句话解释 |
|------|-----------|
| **ORM（对象关系映射）** | **Object Relational Mapping**。通过在 Java 类与数据库表之间建立映射关系，实现直接用操作对象的方式来操作数据库。 |
| **JDBC** | **Java Database Connectivity**。Java 官方定义的规范化底层数据库连接与操作接口，MyBatis 是在 JDBC 之上进行的高度封装与简化。 |
| **动态 SQL** | MyBatis 提供的强大标签（如 `<if>`, `<foreach>`, `<choose>`），允许根据不同的业务条件在运行期动态拼接出最终的 SQL。 |
| **SqlSession** | MyBatis 核心操作接口，代表与数据库的一次会话，内部包含了执行 SQL、提交事务、管理缓存等方法。**注意：它是线程不安全的**。 |
| **预编译 SQL** | 数据库对 SQL 先进行编译，参数位置占位化（`?`）。后续执行直接传入参数即可，避免重复编译，且能彻底封杀 SQL 注入。 |

## 🚀 第一优先级核心考点详解（占位符防注入、一/二级缓存、延迟加载原理与 MP 对比）

### 一、 `#{}` vs `${}` 区别与 SQL 注入防御深挖

这是大厂面试官百考不厌的经典基础考点，要求能解释到 JDBC 预编译的底层本质：

#### 1. `#{}`：预编译参数占位符
*   **解析机制**：MyBatis 在解析 XML/注解中的 SQL 时，会将 `#{}` 统一替换为 JDBC 的占位符 `?`。在底层利用 JDBC 的 **`PreparedStatement`** 进行预编译。执行时，通过 `setXXX()` 方法将真实参数安全注入。
*   **SQL 注入防御**：
    *   **原理**：因为 SQL 的**语法树结构在预编译阶段就已经在数据库中完全固化**。后续传入的任何恶意字符串（如 `' or '1'='1`）都会被强制当成**普通的字面量字符串数据**绑定给占位符，绝对无法参与 SQL 的语法编译，因此能**百分之百杜绝 SQL 注入**。
*   **适用场景**：最常用、最安全的参数传递首选方式。

#### 2. `${}`：纯字面量拼接符
*   **解析机制**：MyBatis 会直接将变量以纯文本字符串的形式，无保留地直接拼接到 SQL 语句中，相当于静态的 String 拼接。
*   **致命缺陷**：**无法防止 SQL 注入**。如果用户传入恶意的输入，会直接篡改 SQL 的语法树结构，直接突破数据库的安全防线。
*   **不得不用的特殊刚需场景**：有的时候，有些 SQL 结构**无法使用预编译占位符 `?`**，此时必须使用 `${}` 进行字面量拼接：
    1.  **动态指定排序列名或排序方式**：`ORDER BY ${columnName} ${orderType}`。因为如果写成 `ORDER BY #{columnName}`，预编译注入后会变成 `ORDER BY 'price'`（带上了单引号），导致 SQL 语法直接报错失效。
    2.  **动态指定分表/表名**：`FROM ${tableName}`。表名是无法被预编译占位符 `?` 代替的。
*   **安全防范**：在必须使用 `${}` 的场景下，**必须在 Java 业务层进行严格的白名单安全匹配过滤**，确保变量仅能在可控的范围内输入，严防 SQL 注入。

### 二、 MyBatis 一级缓存与二级缓存深度剖析

#### 1. 一级缓存 (Local Cache)
*   **缓存级别**：**SqlSession 会话级别**。默认开启，且无法关闭。
*   **底层结构**：由 SqlSession 内部维护的一个简单的 `PerpetualCache`（底层是一个普通的 `HashMap`）实现。
*   **流转机制**：在同一个 SqlSession 会话中，如果执行了完全相同的 SQL 查询，MyBatis 会首选去当前一级缓存中查找。如果命中直接返回，避免重复与数据库交互。
*   **强失效场景**：
    1.  当前会话结束，SqlSession 被关闭。
    2.  在两次查询之间，当前会话执行了**任意一次写操作（INSERT/UPDATE/DELETE）并提交**。这会导致该 SqlSession 的一级缓存被**立即全部清空**，以防读取到过期脏数据。
    3.  手动执行了 `sqlSession.clearCache()` 强制清空。
    4.  不同的 SqlSession 之间，一级缓存是完全隔离、互不相通的。

#### 2. 二级缓存 (Second Level Cache)
*   **缓存级别**：**Namespace (Mapper 接口) 级别**。跨 SqlSession 共享。默认关闭，需要在 Mapper 配置文件中显式配置 `<cache/>` 手动开启。
*   **强制要求**：二级缓存中缓存的所有 Java 实体对象，**必须强制实现 `Serializable` 序列化接口**。因为二级缓存可能将对象序列化保存至本地磁盘、网络传输或外置的分布式缓存（如 Redis）中。
*   **致命缺陷与脏读大坑（大厂坚决不用二级缓存的原因）**：
    *   **关联多表查询脏读**：二级缓存是基于 Namespace 隔离的。如果 Mapper A 里的 SQL 进行了多表 Join 关联了表 B 的数据。此时，另一个事务在 Mapper B 中更新了表 B 的数据。由于是在 Mapper B 中执行的写操作，它只会清空 Mapper B 的二级缓存，**而 Mapper A 里的二级缓存依然存在且一无所知**。此时，外部通过 Mapper A 依然会读取到二级缓存里的旧脏数据，引发严重的业务数据不一致！
    *   **生产最佳实践**：在真实的分布式、高并发微服务项目中，**强烈建议彻底关闭并不用 MyBatis 二级缓存**。对于缓存的高级控制，首选在业务层引入规范的分布式多级缓存方案（如简历中写到的 `Caffeine + Redis 二级缓存` 架构），做精细的更新剔除与强一致性保障。

### 三、 延迟加载 (Lazy Loading) 核心工作原理

#### 1. 什么是延迟加载？
针对一对多或一对一的关联嵌套查询（如查询订单时关联查询用户信息）。如果只访问订单信息，则延迟加载不会去查询用户信息；只有当在代码中**真正调用 `order.getUser()` 获取用户对象时**，MyBatis 才会动态发送第二条 SQL 去查询用户信息。

#### 2. 底层实现原理
延迟加载的精髓在于：**CGLIB 动态代理 + 方法拦截器**。
1.  **动态代理半成品生成**：当我们在配置文件中开启延迟加载后（设置 `lazyLoadingEnabled = true`），MyBatis 从数据库查出订单数据进行组装时，发现用户属性需要延迟加载。此时，MyBatis 底层会利用 **CGLIB**（或 Javassist）动态代理技术，**为订单实体类在内存中动态生成一个代理子类对象**返回。
2.  **方法调用拦截**：这个代理子类对象中持有一个方法拦截器。当我们在 Java 业务层执行 `order.getOrderNo()` 时，拦截器发现此属性不需要延迟加载，直接返回。
3.  **动态发送 SQL 重建**：一旦我们在代码中调用了 **`order.getUser()`**，方法拦截器会被瞬间触发拦截。它检测到 `user` 属性目前依然是空值，会立即“秘密”向数据库发送对应的关联查询 SQL：`SELECT * FROM user WHERE id = ?`，将查回的用户数据进行反射属性装配。
4.  **无感返回**：装配完毕后，再将填充好数据的 `user` 对象无缝返回给调用者，整个过程在外部调用看来完全是无感知的。

### 四、 MyBatis 与 MyBatis-Plus 的互补关系

*   **MyBatis**：属于底座骨架。它极其擅长处理**超长、复杂的多表 Join 联查以及报表统计 SQL**。开发人员可以在 XML 文件中手写高度定制的 SQL，对 SQL 拥有绝对的控制权和极致的性能优化空间。缺点是简单的单表 CRUD 也必须手写 XML，开发效率较低。
*   **MyBatis-Plus (MP)**：属于超强辅助（**只做增强，不做改变**）。它对 MyBatis 进行了完美补充：
    1.  **单表 CRUD 零手写**：内置通用 Mapper/Service，直接提供几百个单表增删改查方法，完全消灭简单 SQL 映射。
    2.  **强大的条件构造器 (Wrapper)**：利用 Lambda 链式调用动态安全地构建 `WHERE` 子句，消灭多重判断 SQL 拼接。
    3.  **内置好用插件**：自带物理分页插件、乐观锁插件，大幅简化开发。

## 🎯 简历亮点深度关联与大厂面试预测

### 1. 苍穹外卖公共字段自动填充切面与【MyBatis 拦截器 (Interceptor) 底层应用】
*   **面试官切入点**：
    > “你在项目中提到了基于 MyBatis 的数据访问层设计。对于很多业务表，插入时需要填充 `createTime`、`createUser`，更新时需要填充 `updateTime`、`updateUser`。如果在每个 Service 里写 set 逻辑太冗余，漏写还会引发非空报错。请问在底层你是如何优雅地进行公共字段自动填充的？MyBatis 拦截器原理是怎样的？”
*   **袁志刚专属特训回答模版**：
    1.  **公共字段的 AOP 拦截思想**：为了彻底消灭繁琐的样板代码，我们设计了**自定义注解 `@AutoFill` + MyBatis 拦截器 (Interceptor)** 方案。
    2.  **MyBatis 拦截器四大核心拦截点**：
        MyBatis 底层高度遵循插拔式设计，允许通过插件对以下四大核心对象执行的方法进行 AOP 拦截：
        *   **`Executor`**：核心执行器，负责 SQL 的调度、事务以及缓存管理。
        *   **`StatementHandler`**：语句处理器，负责利用 JDBC 的 Statement 进行 SQL 的预编译与执行。
        *   **`ParameterHandler`**：参数处理器，负责将 Java 方法参数转化为 SQL 占位符的真实值。
        *   **`ResultSetHandler`**：结果集处理器，负责将 JDBC 的 ResultSet 映射转化为 Java 实体对象。
    3.  **自动填充拦截器的硬核落地步骤**：
        *   **定义拦截器**：我们自定义 `AutoFillInterceptor` 类，实现 MyBatis 的 `Interceptor` 接口，并使用 `@Signature` 声明拦截 **`Executor.class`** 内部的 `update` 方法（在 MyBatis 源码中，所有的 INSERT 和 UPDATE 底层在 Executor 层均被视为 `update` 操作）。
        *   **获取操作类型与参数**：当写操作触发时，拦截器截获当前被执行的 `MappedStatement` 实体，通过 `mappedStatement.getSqlCommandType()` 判定当前是 `INSERT` 还是 `UPDATE` 操作。
        *   **反射公共字段填充**：
            1.  我们获取执行 SQL 时传入的实体参数对象 `entity`。
            2.  利用反射扫描 `entity` 的 Class，确认其是否标有 `@AutoFill` 注解。
            3.  如果存在，通过反射动态获取实体的属性名（如 `createTime`、`createUser` 等）。
            4.  利用我们封装的 `BaseContext` (底层基于 **ThreadLocal**) 极速提取当前登录用户的 ID，并获取当前系统时间戳。
            5.  通过反射调用对应的 `setter` 方法，将用户 ID 和时间戳**在内存中安全注入实体**。
        *   **无感放行**：最后调用 `invocation.proceed()` 放行，MyBatis 就会拿着已被我们注入好公共字段的实体，继续往下执行原生的 SQL 执行与落库。这彻底实现了业务层零感知、数据库强约束的优雅自动填充，展现了极强的工业级工程素养。
