## 🔑 前置基础概念速查（必读，5 分钟建立认知底座）

| 概念 | 一句话解释 |
|------|-----------|
| **JVM vs JDK vs JRE** | **JVM**是运行字节码的虚拟机；**JRE**是Java运行环境，包含JVM和核心类库；**JDK**是软件开发工具包，包含JRE和开发工具（如javac），开发必须用JDK。 |

| **多态（Polymorphism）** | 父类型引用指向子类型对象，在运行期（动态绑定）根据对象的实际类型决定调用哪个方法，是AOP和框架的核心设计基石。 |
| **重载 vs 重写** | **重载（Overload）**发生在同一类中，方法名相同但参数列表不同（静态绑定/编译期决定）；**重写（Override）**发生在父子类中，方法签名完全一致（动态绑定/运行期决定）。 |
| **语法糖（Syntactic Sugar）** | 语言提供的某种能增加代码可读性或易用性的语法，在编译阶段会被编译器还原为基础的底层结构（如泛型擦除、foreach、自动装箱等）。 |

## 🚀 第一优先级核心考点详解（反射、动态代理、String、Object 与值传递）

### 一、 Java 反射机制

反射是 Java 被称为“准动态语言”的关键。它允许程序在运行期间借助反射 API 取得任何类的内部信息，并能直接操作任意对象的内部属性及方法。

#### 1. 反射的四个核心类 (java.lang.reflect)
*   `Class`：类元数据对象，代表内存中的一个类。
*   `Constructor`：类的构造方法元数据。
*   `Method`：类的方法元数据。
*   `Field`：类的成员变量元数据。

#### 2. 获取 Class 对象的 3 种方式
*   `Class.forName("全类名")`：多用于配置文件加载，运行期动态加载。
*   `类名.class`：最安全可靠，程序性能最高（无运行期解析，编译期确定）。
*   `对象.getClass()`：适用于已有实例时的类型获取。

#### 3. 反射的优缺点
*   **优点**：赋予程序在运行期的极高灵活性，是所有主流框架（Spring、MyBatis、Jackson 等）的基石。
*   **缺点**：
    1.  **性能开销**：反射涉及动态解析，JVM 无法做 JIT 编译优化，且每次调用都会进行安全权限检查。
    2.  **安全漏洞**：反射可以绕过 `private` 访问限制（通过 `setAccessible(true)`），破坏了封装性，容易引发安全隐患。

### 二、 动态代理机制

代理模式即：不直接调用目标对象，而是通过代理对象来间接访问，从而在不修改目标代码的前提下，动态织入额外逻辑（如日志、事务、安全过滤等）。

#### 1. JDK 动态代理深度剖析
*   **前提条件**：目标类**必须实现一个或多个接口**。
*   **核心 API**：
    *   `java.lang.reflect.Proxy`：利用 `newProxyInstance(ClassLoader loader, Class<?>[] interfaces, InvocationHandler h)` 动态创建代理实例。
    *   `java.lang.reflect.InvocationHandler`：自定义拦截逻辑的核心接口，重写 `invoke(Object proxy, Method method, Object[] args)`。
*   **底层原理**：JVM 在内存中动态生成一个以 `$Proxy0` 命名的新 Class 文件。这个类继承了 `Proxy` 并实现了目标类的所有接口。当调用方法时，它会将请求转发给持有的 `InvocationHandler.invoke` 方法。

#### 2. CGLIB 动态代理深度剖析
*   **前提条件**：目标类**不能是 final 类**（因为继承关系），方法不能是 final/private 方法。
*   **核心 API**：
    *   `net.sf.cglib.proxy.Enhancer`：用于生成子类代理。
    *   `net.sf.cglib.proxy.MethodInterceptor`：重写 `intercept(Object obj, Method method, Object[] args, MethodProxy proxy)`。
*   **底层原理**：底层基于 ASM 字节码操作框架。在内存中动态生成目标类的一个**子类**，重写父类的方法进行拦截。

#### 3. JDK 动态代理与 CGLIB 的对比

| 对比维度 | JDK 动态代理 | CGLIB 动态代理 |
| :--- | :--- | :--- |
| **底层实现** | Java 反射机制 + 接口动态类生成 | ASM 字节码库 + 继承生成子类 |
| **目标类限制** | 必须实现接口 | 不能是 `final` 类，不能拦截 `final/static/private` 方法 |
| **生成速度** | 较快（直接生成类元数据） | 较慢（ASM 动态修改字节码并生成子类） |
| **执行速度** | 较慢（依赖反射调用） | 较快（基于 FastClass 索引机制直接调用方法） |
| **Spring 选择** | 如果实现了接口，默认使用 JDK；否则强制使用 CGLIB | 从 Spring Boot 2.x 开始，默认配置全面倾向于 CGLIB |

### 三、 String 核心面试考点（不可变性、常量池、intern）

String 是 Java 中最常用的类，也是面试官极其偏爱深挖的考点。

#### 1. String 为什么是不可变的？
在 JDK 8 中，String 底层使用 `private final char[] value` 存储字符（JDK 9 之后为了节省内存，改为了 `private final byte[] value`，根据编码自动选择 Latin1 或 UTF-16）。
其不可变性由以下几点共同保证：
*   **核心数组私有化且为 final**：`value` 数组被 `private final` 修饰，外部无法直接访问，且初始化后地址不可变。
*   **不提供修改方法**：String 类没有提供任何可以修改 `value` 数组内容的方法（如 setter）。
*   **类本身是 final 的**：String 类被 `final` 修饰，不允许被继承，从而防止子类通过重写方法破坏其不可变性。

**不可变性的硬核好处**：
*   **字符串常量池缓存**：只有不可变，常量池才能安全共享相同的字符串，节省大量内存。
*   **线程安全**：多个线程并发读取同一个字符串对象时，无需任何同步锁，天生线程安全。
*   **哈希码缓存**：由于不可变，它的 `hashCode` 在创建时计算一次后就被缓存（`hash` 字段），后续哈希计算极其高效，特别适合作为 `HashMap` 的 Key。
*   **网络和系统安全**：Java 中的许多安全关键参数（如数据库连接 URL、文件系统路径、反射类名）都是以字符串形式传递的，若 String 可变，容易被恶意篡改。

> [!TIP]
> **String、StringBuffer 与 StringBuilder 区别：**
> *   `String`：不可变，线程安全，效率适中。
> *   `StringBuffer`：可变，线程安全（所有公共方法均加了 `synchronized` 锁），效率较低。
> *   `StringBuilder`：可变，线程不安全，单线程下效率极高，通常用于循环拼接。

#### 2. 什么是字符串常量池（String Pool）？
为了减少 JVM 中创建相同字符串的开销，JVM 在堆中开辟了一块专门用来存储字符串字面量的区域，即字符串常量池。
*   **JVM 演进历史**：
    *   **JDK 6 及以前**：常量池在**永久代 (PermGen)**，容量有限，极易因大量字符串常量导致 `java.lang.OutOfMemoryError: PermGen space`。
    *   **JDK 7**：常量池被移到了**堆 (Heap)** 中，极大地减少了 OOM 风险，且可以使用堆的垃圾回收机制。
    *   **JDK 8**：取消永久代，引入**元空间 (Metaspace)**，但字符串常量池**依然保留在堆 (Heap)** 中。

#### 3. `intern()` 方法的工作原理
`intern()` 是一个 native 方法。其作用是：当调用 `s.intern()` 时，如果字符串常量池中已经存在一个等于此 String 对象的字符串，则返回常量池中该字符串的引用；否则，在常量池中保存当前字符串的引用或将字符串复制进去。

> [!WARNING]
> **JDK 7 前后的 `intern()` 差异（核心高频题）：**
> *   **JDK 6**：如果常量池中没有该字符串，JVM 会在常量池中**拷贝一份完整的对象**，并返回常量池中这个新对象的地址。
> *   **JDK 7+**：由于常量池移入堆中，如果常量池没有该字符串，JVM 不会再拷贝完整对象，而是**直接在常量池中创建一个引用，指向堆中该对象**，从而节省内存。

**经典代码印证分析**：
```java
String s1 = new String("abc"); 
// 这一行在内存中创建了两个对象：
// 1. 常量池中的字面量 "abc"
// 2. 堆中的 new String("abc") 对象。s1 指向堆中的对象。
String s2 = s1.intern(); // 发现常量池中已有 "abc"，直接返回常量池中 "abc" 的引用给 s2
System.out.println(s1 == s2); // 输出 false （一个是堆对象，一个是常量池对象）

String s3 = new String("1") + new String("1"); 
// 这一行在堆中创建了 "11" 对象，但此时字符串常量池中并没有 "11" 字面量。s3 指向堆中这个 "11" 对象。
s3.intern(); 
// JDK 7+ 发现常量池中没有 "11"，于是在常量池中创建一个引用，直接指向堆中的 s3 对象。
String s4 = "11"; 
// s4 声明时会去常量池寻找，找到了刚才指向 s3 的引用，所以 s4 实际上拿到的就是 s3 的地址！
System.out.println(s3 == s4); // JDK 7+ 输出 true！
```

### 四、 Object 核心方法与 `==` vs `equals`

#### 1. `==` vs `equals()` 深度辨析
*   **`==` 运算符**：
    *   比较基本数据类型：比较的是**具体数值**是否相等（如 `int a = 1; double b = 1.0; a == b` 返回 `true`）。
    *   比较引用数据类型：比较的是两者的**内存地址**是否相等（即是否指向堆中的同一个对象）。
*   **`equals()` 方法**：
    *   它是 `java.lang.Object` 类中的非静态方法。
    *   如果类**没有重写** `equals()` 方法，默认底层就是用 `==` 进行地址比较：
        ```java
        public boolean equals(Object obj) {
            return (this == obj);
        }
        ```
    *   如果类**重写了** `equals()` 方法（如 `String`、`Integer`、`BigDecimal` 等），则会根据重写逻辑去比较**对象的内容/数值**是否相等。

#### 2. Object 类的 11 个核心方法
Object 是所有类的父类，它定义了以下 11 个核心方法：
1.  `getClass()`: native 方法，返回对象的运行期 Class 对象，是反射的源头。
2.  `hashCode()`: native 方法，返回对象的哈希码，主要用于哈希表（如 `HashMap`）定位槽位。
3.  `equals(Object obj)`: 比较两对象是否相等。
4.  `clone()`: native 方法，创建并返回此对象的浅拷贝。必须实现 `Cloneable` 接口，否则抛出 `CloneNotSupportedException`。
5.  `toString()`: 返回对象的字符串表示（默认是 `类名@十六进制哈希码`）。
6.  `notify()`: native 方法，唤醒在该对象监视器上等待的单个线程。
7.  `notifyAll()`: native 方法，唤醒在该对象监视器上等待的所有线程。
8.  `wait()`: 导致当前线程释放锁并进入等待状态，直到被唤醒。
9.  `wait(long timeout)`: 等待一段时间，超时后自动唤醒。
10. `wait(long timeout, int nanos)`: 更高精度的等待。
11. `finalize()`: 垃圾回收器回收对象前的回调方法（从 Java 9 开始被标记为 `@Deprecated`，禁止在业务中使用）。

#### 3. `equals` 与 `hashCode` 契约问题
> [!IMPORTANT]
> **黄金契约规则**：
> 1. 如果两个对象通过 `equals()` 方法判断相等，它们的 `hashCode()` 必须相同。
> 2. 如果两个对象的 `hashCode()` 相同，它们通过 `equals()` 并不一定相等（这被称为哈希碰撞）。

**为什么重写 `equals` 时必须重写 `hashCode`？**
因为 Java 中许多集合（如 `HashMap`、`HashSet`）都是基于哈希表实现的。当放入一个元素时，集合会先计算对象的 `hashCode` 定位到哈希桶：
*   如果重写了 `equals` 但没有重写 `hashCode`，即使两个对象内容完全一致，它们的哈希码依然可能不同（由 Object 的默认实现决定，通常与内存地址有关）。
*   此时，这两个本应“相等”的对象会被分配到**不同的哈希桶**中，从而完美绕过 `equals` 的排重逻辑，导致 `HashSet` 中存入重复数据，或者 `HashMap` 无法通过相等的 Key 获取 Value，彻底破坏了集合类的核心机制。

### 五、 值传递 vs 引用传递（Java 只有值传递）

#### 1. 核心理论：Java 只有值传递
在 Java 中，无论参数是基本数据类型还是引用数据类型，方法调用时的参数传递机制**全部都是值传递 (Pass-by-Value)**。
*   **值传递**：方法接收的是实际参数值的一个**副本（Copy）**。
*   **引用传递**：方法接收的是实际参数的**内存地址**本身，对形参的修改会直接修改实参。

#### 2. 基本类型的参数传递
基本类型（如 `int`, `double`）在方法调用时，会将具体数值复制一份传递给方法的形参。形参和实参在栈中是相互独立的两个变量。形参的任何修改，实参根本毫无知觉。

#### 3. 引用类型的参数传递（最容易混淆的陷阱）
引用类型（如对象、数组）在方法调用时，复制的是**对象在堆中的内存地址值**。
*   因为形参和实参保存的地址值是相同的，所以通过形参**修改对象的内部属性**时，实参指向的对象属性也会随之改变（因为它们指向堆中的同一个对象）。
*   但是，如果我们将形参**重新指向一个新对象**（即修改形参变量自身保存的地址值），实参变量保存的地址是绝对不会发生任何改变的！

**经典代码印证深度剖析**：
```java
public class ValuePassTest {
    public static void main(String[] args) {
        Person p1 = new Person("袁志刚", 25);
        Person p2 = new Person("Ethan", 26);
        
        System.out.println("【交换前】p1: " + p1.getName() + ", p2: " + p2.getName());
        swap(p1, p2);
        System.out.println("【交换后】p1: " + p1.getName() + ", p2: " + p2.getName());
        
        changeAge(p1);
        System.out.println("【修改后】p1的年龄: " + p1.getAge());
    }

    public static void swap(Person a, Person b) {
        // 方法内的 a 和 b 分别是实参 p1 和 p2 所存地址的副本
        Person temp = a;
        a = b;
        b = temp;
        // 此时，形参 a 指向了 p2，形参 b 指向了 p1。
        // 但这仅仅是局部变量 a 和 b 的指向互换了，外部 main 方法中的 p1 和 p2 指向依然没有任何改变！
    }

    public static void changeAge(Person p) {
        // p 拿到了 p1 的地址副本，它们指向堆中同一个 Person 对象
        p.setAge(30); // 通过该地址直接修改了堆中对象的属性
    }
}
```
**运行结果**：
```text
【交换前】p1: 袁志刚, p2: Ethan
【交换后】p1: 袁志刚, p2: Ethan    <-- 证明 swap 失败，Java 确实不是引用传递！
【修改后】p1的年龄: 30             <-- 证明通过地址副本能成功修改原对象属性
```

### 1. 动态下发工具白名单、签名检测与【反射机制】
*   **面试官切入点**：
    > “我看到你的 AI Agent 调度管道中，能够根据识别的意图动态下发工具白名单（例如购物车意图仅开放 6 个相关工具），并且通过调用签名检测防止死循环。在 Java 中，你是如何实现这些工具的动态调用和安全签名的？”
*   **袁志刚专属特训回答模版**：
    1.  **动态识别与元数据提取**：在项目启动时，我们利用 Java 的 **反射机制 (Reflection)** 扫描带有特定注解（如 `@AgentTool`）的 Bean。通过 `Class.getDeclaredMethods()` 获取方法元数据，包括方法名、参数类型、返回类型，并利用反射读取方法上的注解描述，将其自动转化为大模型（LLM）所需的 JSON Schema 工具声明。
    2.  **动态下发与反射调用**：当 LLM 决策需要调用某个工具时，它会返回一个工具名称及 JSON 格式的参数。我们根据工具白名单过滤后，利用反射的 `Method.invoke(Object obj, Object... args)` 进行动态执行。
    3.  **调用签名检测与安全防御**：反射调用存在安全风险（如注入、死循环调用等）。我们通过反射提取方法的**签名哈希**，与当前对话上下文中的“调用栈快照”比对。如果发现相同方法在同一次多步编排中被调用且参数一致，即触发“工具调用死循环熔断”。同时，在 `Method.invoke` 之前，通过 Java 的访问控制反射（如 `setAccessible` 限制）和安全沙箱，防止 LLM 通过非法输入探测或调用系统受限 API（如文件系统、系统命令）。

### 2. Spring AI Advisor 链与【动态代理与 AOP】
*   **面试官切入点**：
    > “你的 Agent 调度管道基于 Spring AI Advisor 链实现，且提到用了 AOP 的思想进行拦截和过滤。请问 Spring 中的 AOP 是如何通过动态代理实现的？JDK 动态代理与 CGLIB 有什么区别？它们在你的项目里是如何工作的？请结合具体的接口和组件（如 `CallAdvisor`、`StreamAdvisor`、`ToolCallAdvisor`）谈谈你的底层开发细节。”
*   **袁志刚专属特训回答模版**：
    1.  **代理模式在 Spring AI 中的硬核落地**：
        *   Spring AI 的 `Advisor` 拦截机制就是**责任链模式**与**动态代理**的完美融合。
        *   在我们的 `sky-ai` 客服项目中，核心拦截组件如 `UserContextAdvisor` 实现了 **`CallAdvisor`** 和 **`StreamAdvisor`** 双重接口。这表明它不仅支持同步阻塞式的代理（`adviseCall`），还天然支持高并发下的**流式响应式代理**（`adviseStream`，底层返回 Reactor 响应式流 **`Flux<ChatClientResponse>`**）。
        *   在代理拦截方法内，我们对 `ChatClientRequest` 进行 **`mutate()` 链式代理重构**，如通过 `instructions.add(0, new SystemMessage(contextBlock))` 在首位织入画像上下文，最后返回 `nextCall(chatClientRequest.mutate().prompt(prompt).build())`。这正是经典的 AOP 动态代理增强思想。
    2.  **JDK 动态代理 vs CGLIB 动态代理底层**：
        *   **JDK 动态代理**：基于接口实现。Spring 会为实现了 `Advisor`（如 `CallAdvisor`、`StreamAdvisor`）等标准接口 of the classes，利用 `Proxy.newProxyInstance()` 动态在内存中生成一个字节码代理类。底层是通过实现相同的接口，并在 `InvocationHandler` 的 `invoke()` 方法中通过反射回调目标对象。
        *   **CGLIB 动态代理**：基于继承实现。如果目标类没有实现接口，Spring 会通过 CGLIB 动态生成一个目标类的子类。例如，我们的 `SafeToolCallAdvisor` 并没有实现接口，而是继承自 Spring AI 内置的 **`ToolCallAdvisor`** 基类。此时，Spring 底层就会通过 CGLIB 动态生成一个 `SafeToolCallAdvisor` 的代理子类，重写其方法，在执行 `doAfterCall`/`doAfterStream` 拦截时，通过 `guard()` 对 `ChatClientResponse` 进行 `mutate().chatResponse(fallback).build()` 重构，从而实现熔断截断。
    3.  **性能与适配**：在我们的 Agent 管道中，由于大部分 Advisor 明确实现了 `CallAdvisor`/`StreamAdvisor` 接口，Spring 默认使用 JDK 动态代理；而在遇到继承关系类（如 `SafeToolCallAdvisor` 继承自 `ToolCallAdvisor`）或未实现接口的后端订单业务类时，Spring 会自动降级使用 CGLIB 代理。

### 3. 餐饮 SaaS 金额计算与【BigDecimal 精度陷阱】
*   **面试官切入点**：
    > “在苍穹外卖中，涉及菜品价格、购物车总价以及支付回调退款的计算。你为什么要使用 BigDecimal？如果在开发中误用了 `new BigDecimal(0.1)` 或者用 `equals` 进行价格比较，会发生什么灾难性的后果？你在底层是如何设计的？”
*   **袁志刚专属特训回答模版**：
    1.  **为什么必须用 BigDecimal**：浮点数（`float`/`double`）在计算机底层是用二进制科学计数法表示的，无法精确表示很多十进制小数（例如 `0.1` 无法被精确转换为二进制无限循环小数），计算时会产生微小的精度丢失。在餐饮 SaaS 系统中，日均 1000+ 条账单一旦出现精度偏差，会导致对账失败和财务灾难。
    2.  **初始化陷阱**：绝对不能写 `new BigDecimal(0.1)`，因为这会引入浮点数本身的精度误差（实际上它会变成 `0.10000000000000000555...`）。正确的做法是使用 `new BigDecimal("0.1")` 或者静态工厂方法 `BigDecimal.valueOf(0.1)`（其底层调用的就是 `Double.toString()`）。
    3.  **等值比较陷阱**：绝对不能用 `equals()` 方法来比较两个 BigDecimal 的数值是否相等，因为 `equals()` 不仅比较数值，还会比较**精度（Scale）**。例如 `0.1` 和 `0.10` 精度不同，用 `equals` 比较会返回 `false`。在判断订单总价是否与支付回调金额一致时，必须使用 `compareTo()` 方法，当 `a.compareTo(b) == 0` 时才表示数值完全相等。

## 🛠️ 第二优先级核心考点详解（异常、拷贝、抽象类、序列化、SPI）

### 一、 异常处理机制与 Agent 容错设计
1.  **异常分类**：
    *   `Throwable` 是所有异常和错误的超类。
    *   `Error`：JVM 无法处理的严重错误（如 `OutOfMemoryError`、`StackOverflowError`），程序会直接崩溃。
    *   `Exception`：程序本身可以处理的异常。
        *   **受检异常 (Checked Exception)**：编译期强制捕获（如 `IOException`、`SQLException`）。
        *   **非受检异常 (Unchecked Exception/RuntimeException)**：运行期异常（如 `NullPointerException`、`IndexOutOfBoundsException`）。
2.  **Agent 容错设计最佳实践**：
    *   在 Agent 调用外部工具时，极易因网络超时、三方 API 错误发生异常。我们不能让异常导致整个 Agent 线程崩溃。
    *   **防爆设计**：在反射执行 `Method.invoke` 时，使用 `try-catch` 捕获 `InvocationTargetException`，通过 `getTargetException()` 获取真实的业务异常，并将其转化为对 LLM 友好的“错误提示 JSON”（例如：“由于网络波动，购物车暂时无法添加商品，请引导用户稍后重试”）。这不仅保护了系统，还赋予了 LLM “自愈”的机会。

---

### 二、 深拷贝 vs 浅拷贝
*   **浅拷贝 (Shallow Copy)**：仅复制对象本身和其基本数据类型属性。如果属性是引用类型（如对象、集合），拷贝的仅仅是引用地址，拷贝对象和原对象指向同一个子对象，修改其中一方会导致另一方改变。
*   **深拷贝 (Deep Copy)**：不仅复制对象本身，连同对象内部的所有引用对象也全部递归复制一份，在内存中产生完全独立的全新对象结构。
*   **实现深拷贝的方法**：
    1.  重写 `clone()` 方法并在内部显式克隆引用类型（繁琐，维护成本高）。
    2.  **序列化与反序列化**：将原对象序列化写入流，再反序列化读出，可以天然地实现完美的深拷贝（常使用 `Hutool` 的 `ObjectUtil.cloneByStream` 或 `Jackson`/`Gson` 转化为 JSON 字符串再还原）。

---

### 三、 接口与抽象类的区别

| 对比维度 | 接口 (Interface) | 抽象类 (Abstract Class) |
| :--- | :--- | :--- |
| **修饰符** | 默认为 `public`，变量只能是 `public static final` | 可以有任意修饰符，可以定义普通成员变量 |
| **多继承** | 一个类可以实现多个接口，接口之间可以多继承 | 一个类只能继承一个抽象类（单继承） |
| **设计意图** | 对行为进行约束，侧重于“有没有某种能力（Like-a）” | 代码复用，侧重于“是不是某个事物（Is-a）” |
| **方法实现** | Java 8 前不能有实现，Java 8 引入 `default` 与 `static`，Java 9 引入 `private` 方法 | 既可以有抽象方法，也可以有具体的实现方法 |

---

### 四、 序列化与反序列化
*   **序列化**：将 Java 对象转化为二进制字节流的过程，以便在网络中传输或持久化到磁盘/Redis 中。
*   **反序列化**：将字节流还原为 Java 对象的过程。
*   **常见方案与对比**：
    1.  **JDK 自带序列化**：需要实现 `Serializable` 接口。缺点是效率极低、字节码体积大，且存在严重的安全漏洞（反序列化注入），工业界基本弃用。
    2.  **JSON 方案 (Jackson / Fastjson / Gson)**：可读性极好，跨语言支持强。通常作为前后端数据交互、Redis 缓存对象的首选。
    3.  **二进制 Protobuf / Hessian / Kryo**：序列化后体积极小、速度极快，是高性能 RPC 框架（如 Dubbo）的底层首选。

---

### 五、 SPI 机制 (Service Provider Interface)
*   **概念**：SPI 是一种服务发现机制。它将装配的控制权交到了接口的实现者手里，实现了“接口在核心库，实现由插件注入”的解耦。
*   **应用场景**：JDBC 驱动加载、Spring Boot `META-INF/spring.factories`（或 `META-INF/spring/org.springframework.boot.autoconfigure.AutoConfiguration.imports`）实现的自动装配。
*   **工作机制**：在类的 ClassPath 路径下创建 `META-INF/services/` 目录，新建一个以“接口全限定名”命名的文件，文件内容为该接口所有“实现类的全限定名”。通过 `ServiceLoader.load(Interface.class)` 动态加载。

---

## 📝 第三优先级核心考点详解（基本类型、装箱拆箱、语法糖与常识）

### 一、 基本数据类型与自动装箱/拆箱
1.  **八大基本数据类型**：
    *   数值型：`byte(1字节)`、`short(2字节)`、`int(4字节)`、`long(8字节)`、`float(4字节)`、`double(8字节)`
    *   字符型：`char(2字节)`
    *   布尔型：`boolean(未定义，JVM中通常用int或byte表示)`
2.  **自动装箱与拆箱**：
    *   **装箱**：基本类型转换为包装类型，底层调用 `Integer.valueOf(i)`。
    *   **拆箱**：包装类型转换为基本类型，底层调用 `Integer.intValue()`。
3.  **包装类整型缓存池陷阱 (IntegerCache)**：
    *   在 `-128 ~ 127` 的区间内，`Integer.valueOf(i)` 会直接从缓存池中读取已创建的对象，而不是新建。
    *   **代码检验**：
        ```java
        Integer a = 127;
        Integer b = 127;
        System.out.println(a == b); // 输出 true （读缓存，地址相同）

        Integer c = 128;
        Integer d = 128;
        System.out.println(c == d); // 输出 false （超出缓存范围，重新 new 了对象，地址不同）
        ```
    *   **大厂规范**：所有包装类对象之间的值比较，**必须全部使用 `equals()` 方法**，杜绝使用 `==`。

---

### 二、 核心语法糖
Java 语法糖是编译器在编译期做的一种“小魔法”，它让代码写起来更简练，但在编译成 `.class` 字节码后，会被还原为最基本的底层逻辑。

1.  **泛型擦除**：Java 的泛型是“伪泛型”。在编译期，所有的泛型信息都会被擦除掉，并替换为原始的 `Object` 类型（如果有上限，则替换为上限类型，如 `T extends Number` 会被擦除为 `Number`），并在读取时插入强转指令。这也是为什么无法在运行期直接通过 `new T()` 或 `instanceof T` 来使用泛型。
2.  **try-with-resources**：
    *   传统流关闭需要在 `finally` 里手动写复杂的非空判断并关闭。
    *   使用 `try-with-resources` 后，只要实现了 `AutoCloseable` 接口的流资源，都可以写在 `try(...)` 的括号里，编译器会在编译后自动在底层生成对应的 `close()` 调用及完美的异常抑制逻辑，保证资源安全释放，防止连接泄露。
