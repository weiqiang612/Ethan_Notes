## 一、Week 5 阶段定位

### 周目标

当 Agent 同时拥有知识库、实时业务 Tool 与受控写操作时，建立正确的数据来源决策链路。交付 **Strategy-based RAG Tool Router**，而不是让模型自由猜测或自由调用全部能力。

### 核心边界

```text
用户请求
  ↓
Intent / Policy Router
  ↓
route + allowed_capabilities + reason
  ├─ knowledge  → RAG Retriever Tool → 带来源的回答或拒答
  ├─ business   → 实时 Business Tool → 基于实时事实的回答
  ├─ operation  → 草稿 / 确认 API → 受控写操作
  └─ ambiguous  → 追问或拒答
```

- RAG 只回答稳定的知识：退款政策、配送规则、菜品说明。
- Business Tool 只回答实时事实：订单状态、退款到账、账户信息。
- 写操作必须走 Week 3 的任务确认闭环。
- LangChain 本周只作为 Loader、Splitter、Vector Store、Retriever 等检索组件；Agent Loop、Tool Policy 与实际执行仍由 Week 4 的 Native Agent Runtime 控制。

## Day 31：Intent / Policy Router 与来源边界

### 今日目标

让策略层先给出候选能力范围，再让模型在允许范围内辅助理解；避免 LLM 自主决定所有数据源。

### 学习输入

- 稳定知识、实时事实、写操作与歧义请求的边界。
- 策略路由是业务规则，不是仅靠关键词匹配的玩具分类器。

### 编码实践

实现 Router 输出：

```json
{
  "route": "knowledge | business | operation | ambiguous",
  "allowed_capabilities": ["knowledge_search"],
  "response_mode": "answer | create_draft | ask_clarification | refuse",
  "reason": "stable policy question"
}
```

规则示例：

- “退款多久到账？” → `knowledge`。
- “我的订单退款到账了吗？” → `business`。
- “取消订单 123” → `operation`，只允许创建草稿。
- 无法判断具体订单或问题含义 → `ambiguous`，追问而不是猜测。

### AI 辅助任务

> 请从 Agent 可靠性角度 Review 我的来源策略：哪些问题应走 RAG、哪些必须走实时 Tool、哪些必须进入确认闭环？请补充会导致错误数据源选择的歧义例子。

### 验收检查

- 为什么实时订单事实不能由 RAG 回答？
- 策略 Router 的输出为何要包含 reason 与 allowed capabilities？
- 何时应追问而不是选择一个看似合理的工具？

### 当日产出

- 路由规则、歧义案例与单元测试。

## Day 34：路由、检索与回答评测

### 今日目标

用评测集区分“路由错误、检索错误、生成不忠实、工具错误”，不凭感觉调 Prompt 或参数。

### 学习输入

- 最小离线评测集与人工标注。
- 评测结果是改进假设，不是模型自动判分的绝对真相。

### 编码实践

创建至少 20 条 JSON 测试数据，每条包含：

```json
{
  "question": "退款多久到账？",
  "expected_route": "knowledge",
  "expected_source": "knowledge | business | operation | refuse",
  "expected_chunk_ids": ["refund-policy-01"],
  "expected_answer_points": ["到账时效", "例外条件"],
  "should_refuse": false
}
```

记录指标：路由正确性、召回命中/相关性、来源忠实度、回答关键点、拒答正确性。失败分类至少包含：source routing、retrieval、grounding/generation、tool data、policy/confirmation。

### AI 辅助任务

> 请根据我的 RAG + Tool 评测集，检查指标是否能定位路由、检索、回答忠实度、拒答或业务 Tool 的问题。不要用泛化的“准确率高低”替代失败分类。

### 验收检查

- “路由对但回答错”与“路由错”如何区分？
- 为什么 expected chunk 与 expected answer points 都有价值？
- 哪些样本必须人工复核？

## Day 35：Strategy-based RAG Tool Agent 综合交付

### 今日目标

把策略路由、RAG、实时 Tool 与受控操作整合进现有 Native Agent Runtime / Task API，不改变安全边界。

### 编码实践

演示三条链路：

1. “退款多久到账？” → Policy Router → `knowledge_search` → 带来源回答。
2. “我的订单现在退款了吗？” → Policy Router → 实时订单 Tool → 基于实时事实回答。
3. “取消订单 123” → Policy Router → 创建操作草稿 → `wait_confirm`；不直接执行。

Router 先限制可用能力；Native Agent Loop 只在该范围内做工具调用与回答组织。更新 README：来源边界、路由表、RAG baseline、评测结果、已知限制和 Week 6 Workflow 演进方向。

### AI 辅助任务

> 请按 Agent 应用工程师标准 Review 我的 Strategy-based RAG Tool Agent。重点检查来源路由、RAG 引用、实时事实边界、操作确认、Prompt 注入风险、评测覆盖和复杂度取舍。

### 最终验收

#### RAG 能力

- 可加载、切分、检索并引用小型知识语料。
- 有可复现 baseline 与 20 条评测集。
- Hybrid 仅在评测证明确有收益时保留。

#### Agent 能力

- Policy Router 限制允许能力，而非让模型自由调用全部工具。
- RAG 不回答实时业务事实；写操作不越过确认边界。
- 路由、检索、回答与 Tool 失败可被独立定位。

### 当日产出

- Strategy-based RAG Tool Agent、README、评测报告与 Week 5 复盘。
- 建议提交：`week05-strategy-rag-tool-agent`。
