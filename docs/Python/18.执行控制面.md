# 8 周学习执行控制面

> 目的不是让 Day 1 到 Day 56 毫无偏差地完成，而是在面试、实习、困难技术点和精力波动出现时，持续保住核心能力与最终作品。

## 一、按能力里程碑管理

执行层级固定为：

    战略目标：成为 Python Agent 应用开发候选人
      → 周能力目标：例如能实现受控 Tool Calling
      → 每日任务：例如完成 function_call_output 回传

日期只用于安排，不是完成标准。每周是否通过，以“能力 + 证据”判断：可运行代码、测试、设计说明、评测或演示，而不是打卡数量。

## 二、每周控制循环

每周末用 30 分钟完成以下检查，并更新仓库中的 progress.md：

1. **能力检查**：本周新增了什么可独立说明的能力？
2. **证据检查**：对应提交、测试、Demo、ADR 或评测在哪里？
3. **理解检查**：若被问“为什么这样设计”，能否说明替代方案和代价？
4. **风险检查**：下周最可能阻塞什么？是理解、实现范围、外部时间还是环境？
5. **范围决策**：保留 P0，明确删掉、延期或压缩哪些 P1/P2。

## 三、时间预算

### 标准日：4 小时

| 时间 | 只做什么 |
| --- | --- |
| 90 分钟 | P0 概念学习和最小实验设计 |
| 120 分钟 | 核心编码、测试或调试 |
| 30 分钟 | AI Review 与自行修正 |
| 30 分钟 | 日志、设计记录、提交准备 |

### 缩短日：2 小时

只保留 60 分钟 P0 理解或最小验证，以及 60 分钟核心编码。取消扩展阅读、性能优化、额外实验和美化文档；不要把所有环节平均缩水。

### 最低维护日：30—60 分钟

适用于实习或突发事务：阅读一个 P0 小节或修复一个小测试，再留下一条进度记录。连续性比“补完今天所有内容”更重要。

## 四、停止扩展规则

出现任一情况时，暂停新增技术栈：

- 已能用 FastAPI、原生 Runtime、RAG、LangGraph、工具治理覆盖目标岗位的核心要求；
- 新技术无法进入最终作品或不能解决已知问题；
- 新实验挤压了面试准备、核心测试或项目整理；
- 当前 P0 能力还没有可复现证据。

禁止以 Kubernetes、微服务拆分、自研 Agent 框架、复杂前端或多 Agent 作为“补进度”手段。

## 五、最终验收

结束时不要求所有扩展项完成，但必须有可验证证据证明：Python 工程结构、类型、异常、测试、异步；Tool Calling、RAG 边界、Workflow、人工确认、Checkpoint、评测；Docker、Trace、Audit、幂等与未知状态处理。

具体延期、优先级和面试插队规则见同目录的 19—21 号文档。
