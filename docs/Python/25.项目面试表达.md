# 受控业务操作 Agent：项目面试表达

## 一、简历版

> 基于 FastAPI 与 LangGraph 构建取消订单受控 Agent：将 LLM 限定为意图识别和工具调用建议，后端通过 Tool Policy 控制权限、参数和业务校验；高风险操作采用人工确认、Checkpoint 恢复、幂等执行与审计追踪。

使用前删除尚未实际实现的能力，并替换为真实测试或演示结果。

## 二、90 秒展开版

### 背景

大模型可以理解用户意图并提出操作建议，但订单取消属于业务写操作，不能允许模型直接执行。

### 方案

系统将模型与执行权隔离：FastAPI 接收任务；Native Runtime 接收模型的工具建议；Tool Policy 负责白名单、权限、参数与业务状态校验；确认后的写操作交给可恢复 Workflow 执行，结果记录 Trace 和 Audit。

### 三个难点

1. **Tool 治理**：模型输出只是建议，可信后端拥有最终执行权。
2. **暂停恢复**：用户稍后确认时，使用同一任务状态恢复，并重新检查订单、权限和幂等键。
3. **未知执行状态**：下游超时不直接视为失败，进入 unknown 并通过查询或对账判断，避免重复写入。

### Trade-off

没有采用完全自主规划的 Agent。高风险业务追求确定性、可审计和可恢复，因此采用 LLM + 确定性策略层 + Workflow 的混合模式；代价是流程更受约束、实现和状态管理更复杂。

## 三、高频追问与回答边界

| 问题 | 回答主线 | 必须补的真实证据 |
| --- | --- | --- |
| 为什么不用普通 Chain？ | 确认和恢复需要持久状态与明确迁移；简单读操作仍留在 Runtime。 | 工作流图、恢复测试 |
| 为什么模型不能直接执行 Tool？ | 模型不可信；权限、Schema、业务校验与幂等必须服务端控制。 | Policy 测试、拒绝样例 |
| 为什么 RAG 不查订单？ | 订单是实时权威数据，应走业务 Tool；RAG 只服务稳定知识。 | 路由评测集 |
| 超时如何处理？ | 可能已执行但响应丢失，进入 unknown，再查或对账。 | unknown 状态测试 |
| 为什么不做多 Agent？ | 当前单一受控流程尚无角色拆分收益，会引入协调与观测复杂度。 | ADR 或范围说明 |

## 四、演示顺序

1. 创建取消订单任务；
2. 展示模型建议与 Policy 层拦截或放行；
3. 展示等待确认的任务状态与审计事件；
4. 确认后展示重新校验、执行和幂等保护；
5. 展示一条拒绝或 unknown 失败案例。

只演示真实实现过的路径，不能用口述替代证据。
