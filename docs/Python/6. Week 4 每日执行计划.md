## 一、Week 4 阶段定位

### 周目标

在不依赖 LangChain 的前提下，理解并实现原生 Responses API 的工具调用闭环：模型提出调用建议，应用校验并执行允许的工具，将工具结果回传模型，再获得最终回答。

本周不会绕过 Week 3 的 API 与确认边界。任务入口仍是 `POST /api/tasks`；模型只替换内部意图理解与只读工具选择能力。取消订单等写操作只能生成草稿，仍需通过 `POST /api/tasks/{task_id}/confirm` 完成后端确认执行。

### 核心原则

```text
LLM 负责：理解输入、提出工具调用建议、基于工具结果组织回答
Application 负责：工具白名单、参数校验、权限/确认、实际执行、状态、审计与循环上限
```

模型输出不是权威指令。任何工具参数都必须在后端重新解析、校验并经过 AgentCore 策略层。

### Native Agent Runtime 数据流

```text
User Request
  ↓
Agent Loop
  ↓
LLM Response（仅提出 function_call 建议）
  ↓
Tool Policy Layer（白名单、权限、schema、业务状态、确认边界）
  ↓
Tool Executor
  ↓
function_call_output（保留对应 call_id）
  ↓
Agent Loop 或 Final Response
```

多工具调用的数据契约必须清晰：模型返回 `type=function_call`、`call_id`、工具名与 arguments；运行时经 Tool Registry、策略和校验后执行；再以同一个 `call_id` 返回 `type=function_call_output`。没有 `call_id` 关联时，多工具调用结果不可安全匹配。

### 本周核心产出

```text

└── labs/

        ├── app/
        │   ├── main.py
        │   ├── llm/client.py

        │   ├── agent/loop.py

```

`.env` 不提交；只有 `.env.example` 描述变量名。单元测试必须使用 Fake LLM Client 与 Fake Tool，不依赖真实 API key 或付费模型调用；真实 API 冒烟测试仅作为显式、可选的本地测试。

## Day 22：Responses API 与 LLM Client 边界

### 今日目标

理解 Responses API 的输入、输出、响应 ID 与 usage 信息，并用 LLM Client 隔离 SDK 细节。

### 学习输入

- OpenAI 官方：Responses API 迁移与 Function Calling。
- 重点：`responses.create` 返回的是包含 output 项的响应对象；不要将它简化为字符串或沿用 Chat Completions 的可变 `messages` 心智模型。

### 编码实践

- 在 `llm/client.py` 定义窄接口，例如 `create_response(input, tools, instructions)`；业务层不得直接调用 SDK。

## Day 24：Structured Output 与参数校验

### 今日目标

区分“结构化提取结果”和“工具调用参数”，并在应用层进行二次校验。

### 学习输入

- OpenAI Structured Outputs 与 Pydantic schema。
- 重点：结构化输出帮助获得可解析格式，但不替代服务端的业务校验。

### 编码实践

定义意图提取等结构化结果，例如：

```python
class IntentResult(BaseModel):
    intent: Literal["query_order", "query_menu", "request_cancel_order", "unknown"]
    confidence: float = Field(ge=0, le=1)
```

同时为每个工具定义独立参数模型。模型给出的参数必须经 Pydantic 解析、字段白名单、用户归属与业务状态检查；校验失败时不得调用工具。

## Day 25：Function Calling 与 Tool Adapter

### 今日目标

实现模型“提出函数调用”到应用“受控执行函数”的转换，理解模型不会直接执行 Python 函数。

### 学习输入

- OpenAI Function Calling：tool schema、`function_call` output item、`function_call_output` 回传。
- 只开放 `query_order`、`query_menu` 等只读工具；写操作只开放“创建取消草稿”的受控能力，绝不直接取消订单。

### 编码实践

在 `agent/tool_adapter.py`：

- 将允许的 Python Tool 转换为 function schema。
- 建立工具名称白名单与参数模型映射。
- 解析模型返回的 `function_call`，校验参数后调用既有 AgentCore / Tool。
- 将成功或失败的脱敏结果编码为 `function_call_output`，保留原始 `call_id`。

未知工具、重复调用、非法参数和策略拒绝均输出明确的工具结果，不允许绕过策略层。

## Day 26：原生 Agent Loop 与 Tool Policy Layer

### 今日目标

完成可测试、有限轮次的工具调用闭环，而不是无限 `while True`。

### 学习输入

- Function Calling 的多轮调用模式。
- 认识 Responses 可使用 response chain；本周学习重点是显式保存并回传 output items，以看清工具结果如何进入下一轮上下文。

### 编码实践

实现 `agent/loop.py` 与显式的 Tool Policy Layer。Agent Loop 只编排 response 与终止条件，不直接执行 Tool；Tool Policy Layer 负责白名单、权限、参数 schema、业务状态与确认边界，Tool Executor 才负责实际调用。

```text
创建 response
  ↓
检查 response.output 中的 function_call
  ↓
校验并受控执行每个调用
  ↓
将 response.output 与对应 function_call_output 组成下一轮 input
  ↓
达到最终文本、拒绝、错误或最大轮次时终止
```

循环必须设置最大轮次、允许工具集合、每轮 telemetry。若无工具调用，读取最终文本；若达到上限，返回明确的受控失败，不伪装为最终回答。

### AI 辅助任务

### 验收检查

- 为什么不能只把工具结果 append 到一个字符串列表？
- 哪些终止条件必须存在？
- 工具异常应如何回传给模型，同时如何避免泄露内部细节？

## Day 27：可靠性、成本与遥测

### 今日目标

为 LLM 调用与工具循环设置预算、超时、重试边界和最小可观测证据。

### 学习输入

- 请求 timeout、可重试错误与幂等边界。
- token usage、模型延迟、轮次、工具调用数与 request/task 关联。

### 编码实践

增加以下控制：

- `max_tool_iterations` 与每任务最大工具调用数。
- LLM 调用 timeout；仅对明确安全的、无副作用的连接失败做有限重试。
- 不自动重试状态变更 Tool；若请求已发出但结果未知，状态必须标记为未知/待核实。
- 区分执行状态：`pending`、`running`、`success`、`failed`、`unknown`。timeout 不自动等于 `failed`；写操作在结果未知时必须查询确认或转人工处理。
- 记录 request ID、task ID、response ID、模型名、耗时、usage、轮次、工具名、结果类别；不记录完整 Prompt、密钥或敏感 Tool 输出。

本周只记录 token usage，不承诺根据价格表计算精确货币成本；价格与模型可变，应在实际部署时按当期价格配置。

每个任务至少输出一条结构化 Agent Trace：

```json
{
  "task_id": "001",
  "model": "...",
  "iterations": 2,
  "tool_calls": 1,
  "input_tokens": 500,
  "output_tokens": 200,
  "latency_ms": 2300,
  "status": "success"
}
```

### AI 辅助任务

> 请以生产 Agent Review 方式检查我的可靠性控制：死循环、无意义重试、重复工具调用、超时后的未知状态、token 预算和日志泄露分别如何处理？

### 验收检查

- 为什么模型请求重试和写工具重试不能用同一策略？
- 为什么 token 统计不等于精确成本结算？
- 超时后如何区分“未执行”“执行失败”“执行结果未知”？

### 当日产出

- Loop 预算、遥测字段、失败路径与单元测试。
- 建议提交：`day27-agent-loop-guardrails`。

## Day 28：Native Agent Runtime Prototype 综合交付

### 今日目标

将原生 LLM Agent Loop 接入 Week 3 的任务 API，保持 API 契约与安全确认不变。

### 编码实践

- `POST /api/tasks` 仍是唯一任务入口；内部由 AgentService 选择原生 Agent Loop 处理自然语言请求。
- 演示“查询订单 123”：模型提出 `query_order` 调用，应用执行只读 Tool，回传 `function_call_output`，模型生成最终回答。
- 演示“取消订单 123”：模型最多创建操作草稿，返回 `wait_confirm`；确认接口收到 `confirmation: true` 后，必须重新校验用户、确认令牌、订单当前状态与幂等键，不能直接恢复旧 State 执行。
- 用 Fake Client 覆盖：直接最终回答、一次只读工具调用、危险工具被策略拦截、未知工具、非法参数、工具失败、最大轮次。
- 固定测试目录：`test_agent_loop.py`、`test_tool_policy.py`、`test_function_call.py`、`test_fake_llm.py`。
- 真实 API 冒烟测试可选且显式标记；不得成为测试套件的默认依赖。

### AI 辅助任务

> 请按大模型应用工程师标准 Review 我的 Native Responses Agent。重点检查 Function Calling 责任链、output 回传、参数校验、Agent Loop 终止、安全边界、遥测与 Spring AI 的对照口径。

### 最终验收

#### LLM 能力

- 能解释 Responses API、Function Calling、Structured Output 的不同职责。
- 能实现模型 → 工具建议 → 应用执行 → 工具结果回传 → 模型最终回答的闭环。

#### Agent 工程能力

- LLM SDK 仅位于 LLM Client 层；FastAPI Router 不直接调 SDK 或 Tool。
- 所有模型工具参数均经过后端校验与策略层。
- Loop 有轮次、工具、timeout 与 telemetry 控制。
- 写操作未绕过 Week 3 的确认 API。
