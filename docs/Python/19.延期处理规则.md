# 延期处理规则

## 触发条件

满足任一条件即进行延期评估，而不是继续硬追日程：

- 一个 P0 任务连续两次学习时段未取得可验证进展；
- 周目标完成度不足以支持下周 P0 依赖；
- 外部事件占用了两个以上标准日；
- 为完成当前任务已开始牺牲测试、理解或安全边界。

## 第一步：识别延期类型

| 类型 | 典型现象 | 首选处理 |
| --- | --- | --- |
| A：理解不足 | 不理解 async、状态机或工具调用生命周期 | 回到官方资料与最小实验，增加 P0 学习时间 |
| B：实现过大 | Runtime 或 Graph 一次塞入过多工具、存储、接口 | 缩小到一个场景、一个工具、一种持久化方案 |
| C：价值不足 | Hybrid RAG、复杂 rerank 或部署细节没有改变核心能力 | 删除或移入 P2 backlog |
| D：外部打断 | 面试、实习、健康或环境问题 | 进入面试模式或维护模式，不补偿式熬夜 |

## 第二步：三问决策

对延期任务依次回答：

1. 后续 P0 是否依赖它？
2. 它是否是目标岗位高频追问能力？
3. 它是否影响最终作品的完整闭环？

| 结果 | 决策 |
| --- | --- |
| 任一为“是”，且任务属于核心机制 | 缩小实现范围后完成，不能跳过 |
| 三项均为“否” | 删除或移入 P2 backlog |
| 有价值但不阻塞后续 | 延期到周末或 Week 8 整理期 |

## 第三步：写出调整记录

每次调整在 progress.md 写四行：

    原任务：
    延期原因与类型：
    新范围或删除项：
    保留的验证证据与重新开始条件：

这样以后复盘的是“做了什么工程取舍”，不是“计划为什么失败”。

| 模块 | 正常范围 | 压缩后必须保留 | 可删除 |
| --- | --- | --- | --- |
