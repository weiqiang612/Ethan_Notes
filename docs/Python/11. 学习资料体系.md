# Python Agent 学习资料体系

> 对应《Python Agent 工程能力提升计划》Week 1—Week 8。目标不是收集资料，而是让每个学习主题都有可验证的输入与代码产出。

## 使用规则

1. **P0 主资料优先**：先读官方资料中指定的小节，再完成当天代码；看不完不扩展到其他教程。
2. **P1 补充资料按需查阅**：用于解释机制、补足困惑，不替代实践。
3. **P2 书籍、论文和源码只做定向阅读**：带着问题读，阅读后留下四问笔记。
4. 每次资料学习必须绑定一个产出：代码、测试、设计记录或失败样例；没有产出不算完成。
5. 版本会变化。开始一个新模块前，先确认文档与 SDK 的当前版本；以官方文档为准。

| 优先级 | 含义 | 使用方式 |
| --- | --- | --- |
| P0 | 本周必读的官方资料 | 按指定顺序阅读并动手实现 |
| P1 | 概念补充或测试、工程参考 | 遇到对应问题时定向查阅 |
| P2 | 书籍、论文、源码 | 只围绕一个明确问题阅读 |

## Week 4：原生 LLM Agent Runtime

**目标**：理解模型只会提出工具调用建议；执行权属于后端 Runtime。

| 资料 | 优先级 | 阅读范围与问题 | 对应产出 |
| --- | --- | --- | --- |
| [OpenAI Responses API 迁移指南](https://developers.openai.com/api/docs/guides/migrate-to-responses) | P0 | 理解响应对象与多轮输入组织，不追求记住全部参数。 | 原生 Runtime 的模型客户端适配层 |
| [Function Calling 指南](https://developers.openai.com/api/docs/guides/function-calling) | P0 | 理解工具定义、function_call、function_call_output 与 call_id 关联。问题：为什么模型不能直接执行工具？ | Tool Registry、Policy Layer、Executor |
| [Structured Outputs 指南](https://developers.openai.com/api/docs/guides/structured-outputs) | P0 | 用结构化模型输出约束意图、操作草稿或结果摘要；仍须服务端业务校验。 | Pydantic schema 与失败分支 |
| [OpenAI Python SDK](https://github.com/openai/openai-python) | P1 | 只查当前 SDK 的 Responses 调用方式；开始前确认版本。 | 真实客户端可替换，默认测试使用 Fake Client |

本周固定数据流：

    User Request
      → Agent Loop
      → LLM Response（仅建议）
      → Tool Policy Layer
      → Tool Executor
      → function_call_output（携带 call_id）
      → 下一轮或 Final Response

**停止条件**：Fake Client 覆盖直接回答、允许工具、危险工具拦截、循环上限；写操作只生成草稿并走确认 API。

## Week 5：策略路由的 RAG + Tool

**目标**：根据数据权威性选择能力，而不是让模型自主决定一切。

| 资料 | 优先级 | 阅读范围与问题 | 对应产出 |
| --- | --- | --- | --- |
| [LangChain Retrieval 文档](https://docs.langchain.com/oss/python/langchain/retrieval) | P0 | 文档、切分、向量存储、retriever、检索链路。重点：检索是受控能力，不是业务事实来源。 | Retriever Tool 与来源元数据 |
| [RAG 原始论文](https://arxiv.org/abs/2005.11401) | P2 | 只理解“参数化记忆 + 外部检索”的动机，不深读公式。 | 一页 RAG 适用边界笔记 |
| 评测样例集 | P0 | 自建至少 20 条：知识查询、业务查询、写操作、歧义/拒答；记录预期来源和失败原因。 | evals/rag_tool_cases 文件 |

先实现 **向量检索基线 + 元数据过滤 + 策略路由**。仅当评测证明有收益，再尝试 BM25、RRF 或 rerank；不要为了堆技术引入 pgvector 或重排序器。

**停止条件**：知识库只回答稳定规则；实时订单等事实走 Business Tool；写操作必须确认；评测能定位路由、召回、忠实度或回答生成问题。

## Week 6：LangGraph 与可恢复工作流

**目标**：仅把需要暂停、恢复、确认的业务操作放入图；普通读取和知识问答继续用 Week 4 Runtime。

| 资料 | 优先级 | 建议顺序 | 对应产出 |
| --- | --- | --- | --- |
| [LangGraph Overview](https://docs.langchain.com/oss/python/langgraph/overview) | P0 | State → Node → Edge → 条件路由 → Persistence → Interrupt | 取消订单工作流骨架 |
| [LangGraph Persistence](https://docs.langchain.com/oss/python/langgraph/persistence) | P0 | thread_id、checkpoint、恢复语义。问题：它与长期 Memory 有何不同？ | 可恢复任务状态 |
| [LangGraph Interrupts](https://docs.langchain.com/oss/python/langgraph/interrupts) | P0 | interrupt / resume 与重新执行语义；恢复前为什么要重新校验？ | 人工确认节点 |

本周只选择一种最终持久化方案。测试允许内存 checkpointer；最终 pause/resume 必须用一个可验证的持久化实现。

**停止条件**：同一 thread_id 可恢复；写节点幂等；恢复前重新检查权限、订单状态和幂等键；能清楚区分 Checkpoint 与 Memory。

## 源码阅读路线与四问法

两个月内的顺序固定为：

    FastAPI：看 Web 分层与依赖边界
      → LangChain：看检索抽象
      → LangGraph：看状态、持久化与中断
      → 成熟项目：看 README、测试和工程取舍

每次源码阅读控制在 **30—45 分钟**，只产出一张记录：

| 问题 | 必须写出的答案 |
| --- | --- |
| 为什么存在？ | 它在架构中的位置与前置条件 |
| 解决什么问题？ | 没有它时会出现的具体失败或复杂度 |
| 替代方案？ | 手写状态机、普通函数、其他存储或更简单边界 |
| 代价是什么？ | 复杂度、可观测性、性能、测试或运维成本 |

若无法回答四问，回到官方概念文档与最小实验，不继续向下追源码。
