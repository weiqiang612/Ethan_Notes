## 一、Week 3 阶段定位

### 周目标

将 Week 2 的 CLI Agent Core 服务化，交付一个可调用、可测试、职责清晰的 FastAPI Agent API。本周仍不接入 LLM；API 处理的是确定性任务与确认闭环，为 Week 4 原生 Agent Loop 预留替换点。

### 最终分层

```text
HTTP Client
  ↓
FastAPI Router / Schema / Middleware
  ↓
AgentService
  ↓
AgentCore
  ↓
Tool Router / Tools / Task Store
```

- **Router**：解析 HTTP、调用 Service、返回契约；不改 State、不直接调 Tool。
- **Service**：协调任务创建、确认与调用方身份边界。
- **AgentCore**：流程、状态、异常转换、受控执行。
- **Tool**：具体查询/写操作能力。
- **Schema**：请求与响应契约；不等于内部 State。

### 本周 API 契约

本周统一使用任务式 API，避免同时出现模糊的 `/api/chat` 与 `/api/tasks`：

```text
POST /api/tasks                    创建查询或待确认任务
POST /api/tasks/{task_id}/confirm  确认指定任务
GET  /health                       健康检查
```

`user_id` 仅作为本周实验中的调用方标识，不代表真实身份认证；Week 7 再讨论认证、授权与可信身份来源。

## Day 17：Pydantic 数据契约

### 今日目标

建立输入、输出、确认操作三类独立 API Schema，并在边界完成运行时校验。

### 学习输入

- Pydantic / FastAPI：`BaseModel`、`Field`、请求体与 response model。
- 对照 Java DTO + Bean Validation，但不要将 Pydantic 当成内部领域模型的唯一替代。

### 编码实践

定义至少三类模型：

```python
class CreateTaskRequest(BaseModel):
    user_id: str = Field(min_length=1, max_length=64)
    message: str = Field(min_length=1, max_length=1000)

class ConfirmTaskRequest(BaseModel):
    user_id: str = Field(min_length=1, max_length=64)
    confirmation_token: str = Field(min_length=1)

class TaskResponse(BaseModel):
    task_id: str
    status: str
    confirmation_required: bool = False
    answer: str | None = None
    draft: dict[str, object] | None = None
```

`user_id` 在本周只用于匹配同一实验调用方；不得宣称它已完成鉴权。

### AI 辅助任务

> 请解释 Pydantic 为什么适合 API 与 LLM 的结构化边界，并比较它与 Java Bean Validation：运行时校验、错误返回、领域模型分离各有什么差异？

### 验收检查

- 为什么请求、响应和内部 State 必须分离？
- 空 message、超长 message、缺失 token 如何得到一致的 422 校验响应？
- 为什么 Pydantic 不能替代服务层权限判断？

### 学习输入

- 复用 Week 2 的异常分层；HTTP 错误不等于 Python 异常文本。

### 编码实践

- 增加 HTTP middleware：读取或生成 `X-Request-ID`，写入响应头，并与 `task_id` 关联到日志上下文。
- 注册已知领域异常处理器，统一返回：

```json
{
  "success": false,
  "error_code": "TOOL_FAILED",
  "message": "工具执行失败",
  "request_id": "..."
}
```

## Day 20：API 测试矩阵

### 今日目标

通过 API 测试证明分层、确认边界与错误契约，而不是只测试 200 响应。

### 学习输入

- pytest + FastAPI TestClient。
- 回顾 dependency override，测试 API 时不依赖真实外部 Tool。

### 编码实践

建立并自动化以下矩阵：

| 场景 | 预期 |
| --- | --- |
| 健康检查 | 200，稳定响应 |
| 正常查询任务 | 任务完成或正确查询结果 |
| 缺失 / 非法请求字段 | 422，结构化校验错误 |
| Tool 失败 | 统一 `TOOL_FAILED` 错误 |
| 取消订单任务 | `wait_confirm` 与草稿 |
| 确认任务所有者不匹配 | 拒绝，不执行 |
| 无效 confirmation token | 拒绝，不执行 |
| 重复确认 | 幂等结果或明确拒绝，绝不重复执行 |
| request ID | 响应头与错误体可关联 |

### 今日目标

### 编码实践

交付以下 API：

```text
POST /api/tasks
POST /api/tasks/{task_id}/confirm
GET  /health
```

创建取消订单任务的响应：

```json
{
  "task_id": "xxx",
  "status": "wait_confirm",
  "confirmation_required": true,
  "draft": {
    "action": "cancel_order",
    "order_id": "123"
  }
}
```

确认接口必须：验证任务存在、用户匹配、确认令牌、当前状态与幂等键；所有检查通过后才允许将任务交给 AgentCore 的受控执行路径。本周可用内存 Task Store，但 README 必须说明重启丢失、单进程限制及 Week 6 持久化演进方向。
