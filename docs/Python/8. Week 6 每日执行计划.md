## 一、Week 6 阶段定位

### 周目标

使用 LangGraph 将“取消订单”这类需要暂停、确认、恢复和审计的业务操作显式建模为可控状态机，交付 **Controlled Business Workflow Agent**。

LangGraph 不是自动规划魔法，也不需要把全部请求图化：Week 5 的知识问答和简单只读查询可继续走策略路由与 Native Agent Runtime；只有多步、可暂停、带副作用的操作流进入 Graph。

### 工作流边界

```text
Intent / Policy Router
  ↓
operation route
  ↓
LangGraph Workflow
  ↓
查询订单 → 风险判断 → 生成草稿 → interrupt 等待确认
  ↓                                      ↑
重新校验 → 受控执行 → 审计 → 结束       Command(resume=...)
```

### 核心原则

- **State** 是本次工作流的最小执行上下文，不是数据库实体或长期 Memory。
- **Node** 只完成一项明确职责；Edge 显式表达业务分支。
- **Checkpoint** 保存相同 `thread_id` 的可恢复执行状态；Memory / Store 是跨任务的长期信息，非本周重点。
- interrupt 后恢复需要相同 `thread_id` 和 `Command(resume=...)`。
- checkpoint 在节点边界保存；中断/恢复时节点可能从函数开头重跑。所有写副作用必须放在可重试、幂等的受控 Tool 后，并在恢复前重新校验。

### 本周核心产出

```text
python-agent-learning/
└── labs/
    └── week06-langgraph-agent/
        ├── app/
        │   ├── graph/state.py
        │   ├── graph/nodes.py
        │   ├── graph/edges.py
        │   ├── graph/workflow.py
        │   ├── tools/order_tools.py
        │   ├── persistence/checkpointer.py
        │   └── api/confirm.py
        ├── tests/
        ├── pyproject.toml
        ├── uv.lock
        └── README.md
```

选择**一种** Checkpointer 作为最终实验实现；本地单元测试可使用内存 Checkpointer，最终暂停恢复演示使用同一选定的持久化实现。不要同时引入 Redis、PostgreSQL 和多套 Checkpointer。

## Day 37：取消订单 State 设计

### 今日目标

设计最小而完整的工作流 State，区分可缓存上下文、权威业务状态和长期信息。

### 学习输入

- TypedDict State、状态合并与字段所有权。
- Week 2 / Week 4 的 `task_id`、确认、幂等与未知执行状态边界。

### 编码实践

定义类似：

```python
class OrderCancelState(TypedDict):
    task_id: str
    thread_id: str
    user_id: str
    order_id: str
    approval_status: Literal["not_requested", "waiting", "approved", "rejected"]
    execution_status: Literal["pending", "running", "success", "failed", "unknown"]
    idempotency_key: str
    audit_event_id: NotRequired[str]
    rejection_reason: NotRequired[str]
```

订单详情可作为短暂快照进入 State，但恢复执行前必须由 Tool 重新查询；模型不能写入 `approval_status=approved`、`execution_status=success` 等权威字段。

## Day 39：Conditional Edge 与显式业务分支

### 今日目标

用条件边显式编码订单存在、风险、确认和执行结果分支，不把关键业务分支交给模型猜测。

### 学习输入

- Conditional Edge、END、拒绝分支与错误分支。
- 将 Policy Router 作为 Graph 之前的入口约束，而不是在 Graph 内重复“自由选工具”。

### 编码实践

实现至少以下分支：

```text
订单不存在       → rejected → END
订单不可取消     → rejected → END
低风险且已确认   → revalidate → execute
需要确认         → create_confirmation → interrupt
执行结果未知     → unknown → END / 人工处理队列
```

所有 Edge 决策必须基于已校验的 State / Tool 结果，而不是模型自然语言结论。

### 验收检查

- Conditional Edge 与普通 if/else 的关系是什么？
- 为什么 `unknown` 不应伪装成 `failed`？
- 哪些分支要进入人工处理而不是自动重试？

## Day 41：Human-in-the-loop 与安全 Resume

### 今日目标

把 Week 3 确认 API 与 LangGraph interrupt / resume 接通，确保恢复不直接执行旧 State。

### 学习输入

- `interrupt()`、`Command(resume=...)` 与相同 thread ID。
- Resume 后相关 Node 可能重跑，因此确认节点前后的代码必须无副作用或可幂等重放。

### 编码实践

实现：

```text
create_confirmation_node
  ↓
interrupt({task_id, draft, confirmation requirements})
  ↓
POST /api/tasks/{task_id}/confirm
  ↓
验证用户、confirmation token、当前 task 状态
  ↓
Command(resume={approval: true}) + 同一 thread_id
  ↓
revalidate_before_execute_node
  ↓
受控 execute_cancel_node
```

恢复前必须重新查询订单并验证权限、订单当前状态与幂等键。确认 API 不是“恢复旧 State 的开关”，而是新的受控输入。

### AI 辅助任务

> 请分析 Human-in-the-loop 中确认、interrupt、resume、重新校验的责任链。为什么恢复前必须重新查订单？节点重跑时哪些副作用最危险？

### 验收检查

- `interrupt` 与 HTTP 确认接口分别负责什么？
- 为什么 resume 需要同一 thread ID？
- 如何处理订单在等待确认期间被其他操作改变？

### 当日产出

- 确认 / resume 闭环、恢复安全测试与流程图。

## Day 42：LangGraph Controlled Order Agent 综合交付

### 今日目标

交付一个可暂停、可恢复、可重新校验、可审计的订单取消工作流。

### 最终流程

```text
Intent / Policy Router
  ↓
Query Order → Risk Check → Create Draft → Interrupt
                                           ↓
Confirm API → Resume → Revalidate → Execute Tool → Audit → END
```

### 测试矩阵

| 场景 | 预期 |
| --- | --- |
| 正常取消 | 成功且有审计记录 |
| 订单不存在 / 不可取消 | 拒绝，不执行 |
| 未确认执行 | 进入 interrupt，不执行 |
| 恢复后订单状态变化 | 重新校验并拒绝或转人工 |
| 重复确认 / 节点重跑 | 幂等，不重复取消 |
| Tool 超时且结果未知 | `unknown`，不伪装失败 |
| 不同 thread ID | 不恢复他人任务 |

### AI 辅助任务

> 请按高级 Agent 工程设计标准 Review 我的 LangGraph Workflow。重点检查 State、Conditional Edge、Checkpoint、interrupt/resume、节点重跑、幂等 Tool、重新校验与审计边界。

### 最终验收

#### LangGraph 能力

- 能解释 StateGraph、Node、Edge、Conditional Edge、Checkpoint 与 interrupt / resume。
- 使用同一 thread ID 暂停并恢复正确的工作流。

#### Agent 工程能力

- 多步操作流程显式化；模型不能直接改变权威执行状态。
- 恢复前重新校验；副作用在节点重跑时保持幂等。
- `unknown`、拒绝、成功与审计结果可追踪。

### 当日产出

- LangGraph Controlled Order Agent、README、测试报告、状态图与 Week 6 复盘。
- 建议提交：`week06-controlled-order-workflow`。

## 二、Week 6 完成定义

完成 Week 6 不等于“会调用 LangGraph API”，而是能将有人工确认和写副作用的业务流程表达为可恢复工作流：状态最小且受控、分支显式、确认恢复安全、节点可重跑、写操作幂等、审计可追溯。
