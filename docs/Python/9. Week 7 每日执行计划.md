## Day 43：Tool Policy 与可信授权输入

### 今日目标

建立 Tool Registry 和策略决策层，明确模型与用户请求都不能自行授予权限。

### 学习输入

- Week 4 Tool Policy Layer 与 Week 6 确认 / resume 边界。
- 区分三种策略决策：`allow`、`require_confirmation`、`deny`。

### 编码实践

实现 Tool Registry，工具声明包含名称、读写类型、参数模型和所需权限。实现：

```python
PolicyDecision = Literal["allow", "require_confirmation", "deny"]
```

策略输入的 `user_id` / role 必须来自可信服务端上下文；不能信任模型输出，也不能把客户端 body 中的 `user_role` 当授权依据。

例如：只读 `query_order` 在权限满足时可以 `allow`；`cancel_order` 在权限满足但未确认时应为 `require_confirmation`，而非简单 `allowed=false`；越权请求为 `deny`。

### AI 辅助任务

> 请从 Agent 安全设计角度 Review 我的 Tool Policy：模型、客户端请求、服务端身份、权限、确认分别能决定什么？请检查我是否混淆了“需要确认”和“无权限拒绝”。

### 验收检查

- 为什么 Tool 权限不能由 LLM 决定？
- `require_confirmation` 与 `deny` 的业务含义有什么不同？
- 为什么 role 必须来自可信服务端上下文？

### 当日产出

- Tool Registry、Policy Decision 表与权限测试。
- 建议提交：`day43-tool-policy-and-permissions`。

## Day 44：参数、业务与安全校验

### 今日目标

将模型 / API 输入依次经过 schema、业务和策略校验，防止合法 JSON 直接变成危险执行。

### 学习输入

- Pydantic runtime validation。
- Tool schema、订单归属、当前订单状态与策略决策的不同责任。

### 编码实践

以取消订单参数为例定义 Pydantic 模型；保持项目内订单 ID 类型一致。执行前必须完成：

```text
Tool Call / API Input
  ↓
Schema Validation
  ↓
Business Validation（订单存在、归属、当前状态）
  ↓
Policy Decision（allow / require_confirmation / deny）
  ↓
Executor
```

Structured Output 或 Function Calling schema 只能帮助解析，不能替代后端的归属与状态校验。

### AI 辅助任务

> 为什么 Structured Output 不能替代后端参数校验？请按 schema、业务、权限、确认四层分析取消订单请求的安全边界。

### 验收检查

- 合法类型但订单不属于当前用户时，在哪层拒绝？
- 为什么业务校验必须发生在确认恢复前后？
- 参数错误、业务拒绝和权限拒绝应如何区分？

### 当日产出

- 参数模型、校验链与负面测试。
- 建议提交：`day44-tool-validation-boundaries`。

## Day 45：幂等、未知执行状态与对账

### 今日目标

为重复确认、节点重跑和网络超时建立原子幂等保护与未知状态后的核实路径。

### 学习输入

- 幂等键的 claim / complete / unknown 状态机。
- 分布式调用中 timeout 不等于操作失败。

### 编码实践

实现 Idempotency Store：以 `task_id + operation` 或受控 idempotency key 原子 claim，记录执行结果；重复请求返回已有结果或进行安全拒绝。不要用“先查再写”的非原子伪实现。

执行状态：`pending`、`running`、`success`、`failed`、`unknown`。写 Tool 超时且远端是否执行不可知时标记为 `unknown`；增加只读 reconciliation / query 能力以核实业务最终状态，必要时转人工处理。禁止自动重新发送同一写操作。

### AI 辅助任务

> 请结合支付系统和 Agent Tool 调用 Review 我的幂等设计：重复确认、节点重跑、客户端重试和网络 timeout 分别如何处理？为什么 unknown 不能简单变成 failed？

### 验收检查

- 为什么幂等 claim 必须原子？
- `unknown` 后下一步是什么，而不是自动 retry？
- 如何证明重复 resume 不会导致重复取消订单？

### 当日产出

- Idempotency Store、unknown / reconciliation 路径与并发/重复测试。
- 建议提交：`day45-idempotency-and-reconciliation`。

## Day 46：Trace、Audit 与脱敏

### 今日目标

分别建立技术 Trace 和不可抵赖的业务 Audit 事件，且两者都可通过 task ID / request ID 关联。

### 学习输入

- Trace：节点、模型、工具、耗时、结果类别、错误码。
- Audit：业务动作、参与者、时间、对象、结果与关联 ID。

### 编码实践

定义：

```text
Trace：task_id, request_id, node/tool, duration_ms, result_kind, error_code
Audit：event_type, task_id, actor_id, order_id(masked), occurred_at, outcome
```

审计事件示例：`ORDER_CANCEL_REQUESTED`、`ORDER_CANCEL_CONFIRMED`、`ORDER_CANCEL_COMPLETED`、`ORDER_CANCEL_RECONCILIATION_REQUIRED`。Audit 事件应追加式、可去重、包含最小必要事实；Trace 不记录完整 Prompt、密钥、完整订单或完整工具输出。

### AI 辅助任务

> 请解释 Agent 系统为什么同时需要 Trace 与 Audit。请 Review 我的字段设计：哪些用于技术排错，哪些用于业务追责，哪些数据必须脱敏或绝不能记录？

### 验收检查

- Trace 与 Audit 分别回答什么问题？
- 为什么审计事件不能只存在普通 debug log？
- task ID、request ID、idempotency key 如何协同排查？

### 当日产出

- Trace / Audit 模型、脱敏规则与关联查询样例。
- 建议提交：`day46-trace-audit-evidence`。

### 编码实践

在既有数据集基础上扩展为 20–30 条代表性样本，至少包含：

```json

  "input": "取消订单 123",

  "expected_tool": "create_cancel_draft",
  "expected_status": "wait_confirm",
  "should_refuse": false,
```

失败分类：source routing、tool schema、business validation、workflow transition、policy / confirmation、idempotency、unknown reconciliation、grounding / answer。评测报告必须能定位失败类别，而不只给“通过率”。

## Day 49：Production-ready Agent Slice 综合加固

### 今日目标

在同一订单取消能力切片上证明正常、拒绝、确认、幂等、未知状态与恢复路径均受控。

### 最终架构

```text
FastAPI Task API
  ↓
LangGraph Workflow
  ↓
Tool Policy → Tool Executor → Business Service
  ↓              ↓
Audit Log      Trace / Evaluation Evidence
```

### 测试矩阵

| 场景 | 验证 |
| --- | --- |
| 正常取消 | 完成且存在审计事件 |
| 无权限 | `deny`，不执行 |
| 未确认 | `require_confirmation` / interrupt，不执行 |
| 非法参数 / 非归属订单 | 校验拒绝 |
| 重复确认或节点重跑 | 原子幂等，不重复执行 |
| Tool timeout | `unknown`，进入核实路径 |
| checkpoint resume | 重新校验当前订单状态 |
| 容器启动 | `/health` 与基础 API 可用 |

### AI 辅助任务

> 请按生产 Agent 工程 Review 我的订单取消能力切片。重点检查可信身份、策略决策、参数/业务校验、幂等、unknown 对账、Trace/Audit、评测证据与 Docker 运行边界。

### 最终验收

#### 安全与可靠性

- Tool Policy 明确 `allow / require_confirmation / deny`。
- 写操作经过参数、业务、权限、确认和幂等校验。
- timeout 的未知结果有核实或人工处理路径。

#### 工程证明

- Trace 与 Audit 可关联且脱敏。
- 评测集能定位失败类别。
- Docker 单服务可构建、启动并通过 `/health`。

### 当日产出

- Production-ready Agent Slice、Docker 证据、评测报告与 Week 7 复盘。
- 建议提交：`week07-agent-slice-hardening`。
