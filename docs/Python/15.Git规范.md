# Git 提交与版本规范

## 提交原则

一次提交只表达一个可理解的意图：一个能力、一个测试集合、一份设计决策或一个可独立回滚的修复。不要使用 update、fix、test 等没有上下文的消息。

格式：

    type(scope): description

常用 type：

| type | 适用场景 | 示例 |
| --- | --- | --- |
| feat | 新增可用能力 | feat(agent-core): add deterministic tool router |
| fix | 修复可复现缺陷 | fix(policy): reject unconfirmed write request |
| test | 新增或调整验证 | test(runtime): cover max iteration guard |
| docs | 设计、说明、学习记录 | docs(design): explain confirmation workflow |
| refactor | 不改变外部行为的重构 | refactor(api): isolate task service dependency |
| chore | 工具、依赖、脚本维护 | chore(deps): add pytest test dependency |

scope 使用稳定模块名，例如 python-core、agent-core、api、runtime、rag、workflow、policy、evals、design。

## 每日与每周节奏

- 当天有独立验证证据后再提交；不强制为打卡制造空提交。
- 每周结束前检查：测试、README 变化、设计记录、未提交文件。
- 每完成一个周目标，在通过验证的提交上打轻量标签：week-01-python-core、week-02-agent-core，依此类推。
- Week 8 最终作品通过干净环境验证后，再打版本标签：v1.0-agent-slice。

## 提交前检查

1. 变更是否只包含当前意图？
2. 是否包含密钥、Token、真实用户数据、私有日志或本机路径？
3. 相关测试或运行命令是否实际执行？
4. README、配置示例和代码是否一致？
5. 失败或限制是否需要同步到设计文档？

## 不做的事

- 不为“看起来活跃”提交未运行的代码；
- 不把大段 AI 生成代码混在无法解释的提交中；
- 不改写已验证历史来隐藏失败实验；失败实验保留在 labs 或复盘文档中。
