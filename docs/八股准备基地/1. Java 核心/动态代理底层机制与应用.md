# 动态代理底层机制与应用

## 1. 大白话：这是什么？解决什么痛点？
**核心概念**：动态代理就是在程序**运行期间**，由 JVM 自动帮你生成一个“替身”对象，代替去执行目标对象的方法。
**解决的痛点**：它能在不修改原有代码的前提下，统一给一堆方法“加料”（比如自动记录日志、处理数据库事务）。如果没有动态代理（即静态代理），你必须手动为每一个需要加料的类写一个对应的代理类，代码会极度臃肿且难以维护。

## 2. 底层机制：JDK vs CGLIB 的巅峰对决
面试官必问的底层区别，只需记住两点：
- **JDK 动态代理（基于接口）**：
  - **原理**：它是 Java 官方自带的。底层是通过在运行时动态生成一个**实现了同款接口**的替身类。
  - **优缺点**：优点是无需第三方依赖，且在现代 JDK 版本中运行效率极高；**致命缺点是只要目标类没实现接口，它就完全瞎了，代理不了**。
- **CGLIB 动态代理（基于继承）**：
  - **原理**：底层是通过操作字节码，动态生成目标类的**子类**来作为替身。
  - **优缺点**：优点是适用面极广，不需要目标类实现任何接口；**缺点是因为基于继承，所以遇到 `final` 修饰的类或方法，它就无能为力了**。

## 3. 🎯 怎么结合我的简历讲？（实战口径）
*(这是最关键的一环，面试时结合项目讲出来，直接秒杀单纯背书的竞争者)*

**在 [[苍穹外卖AI客服]] 或原始外卖项目中的应用场景：**
> **面试口径提炼**：
> “在我的项目中，大量使用了 Spring AOP 来进行统一切面处理，比如**处理公共字段的自动填充（创建时间、更新时间）**以及**数据库事务的控制**。
> 
> 我去扒过 Spring AOP 的底层，发现它其实是智能切换代理方式的。如果我写的 Controller 或 Service 实现了某个接口，Spring 默认会用 **JDK 动态代理**；但如果是没有实现任何接口的普通类，它就会自动切换成 **CGLIB 动态代理**去生成子类。
> 
> 这也是为什么我在开发时，如果在类的内部用 `this.method()` 调用自己的另一个开启了 `@Transactional` 的方法，事务会失效——因为 `this` 调用的只是原始对象，并没有经过 JVM 动态生成的那个‘替身代理对象’。”
