Layer 1 Nginx / OpenResty
Shared-memory dict + Lua scripting. Serves cached responses before hitting any backend.

Key characteristics

  • Storage: lua_shared_dict — shared across all worker processes, survives worker restarts
  • Latency: sub-millisecond (memory read, no network hop)
  • TTL: seconds to a few minutes; short to stay fresh
  • Capacity: typically 10–500 MB per node; limited by RAM allocation
  • Eviction: LRU built into OpenResty's ngx.shared.DICT
  • Ideal for: static-ish content, API responses, rate-limit counters, feature flags

Cache stampede mitigation

  • Use resty.lock to allow only one request through on a miss; others wait and reuse the result
  • Serve stale while revalidating (stale-while-revalidate pattern) for non-critical data
Layer 2 Redis cluster
Distributed in-memory store. Shared across all JVM instances; the authoritative fast cache.

Key characteristics

  • Storage: in-memory, optionally persisted (RDB / AOF snapshots)
  • Latency: 0.5–5 ms (one network round-trip within datacenter)
  • TTL: minutes to hours; set per key with EXPIRE or SET … EX
  • Cluster: data sharded across master nodes; each master has replica(s) for failover
  • Eviction: configurable (allkeys-lru, volatile-lru, allkeys-lfu…)
  • Ideal for: session data, computed aggregates, product listings, user profiles

Consistency patterns

  • Cache-aside: app reads Redis → miss → read DB → write Redis
  • Write-through: writes go to DB and Redis atomically
  • Cache invalidation: delete key on update; let next read repopulate
  • Use Lua scripts or MULTI/EXEC transactions to avoid race conditions
Layer 3 JVM / Caffeine
In-process heap cache. Zero serialization cost; fastest possible reads within a single JVM instance.

Key characteristics

  • Storage: Java heap — plain object references, no serialization
  • Latency: nanoseconds to microseconds
  • TTL: short (seconds to minutes); must be < Redis TTL to avoid serving stale after Redis evicts
  • Eviction: W-TinyLFU algorithm — near-optimal hit rate, low memory overhead
  • Capacity: bounded; size set at build time to prevent GC pressure
  • Scope: local to one JVM — each instance has its own copy
  • Ideal for: hot config, reference data, per-request metadata

Invalidation challenge

  • No built-in cross-JVM invalidation — rely on short TTL or pub/sub via Redis to notify all instances
  • Use expireAfterWrite for correctness; refreshAfterWrite for async refresh
